# Codex integration and profiles decisions

## 2026-10-06 — #154 (phase 1): the Codex terminal beside a second app-server client

Findings, evidence and the fixture: [`docs/research/codex-shared-tui.md`](../research/codex-shared-tui.md)
(`make codex-shared-tui`, `internal/codexshare`). Codex 0.160.1, Herdr 0.9.0. The fixture uses mock inference; one
bounded real-model smoke test (findings §9) ran the phase-2 launch, a per-worker server on the real `~/.codex`, through
Herdr only, and never connected to the user's shared daemon.

| # | Question | Decision |
|---|---|---|
| 1 | Does the terminal still work with a shared server? | **Yes**: the native TUI with `--remote unix://…` keeps typing, slash commands, skills, Ctrl+C, approvals, exit and `codex resume ID --remote` working, and Herdr's start/prompt/read/wait/send-keys and working → idle/done detection with it. A second client shares the thread, and its async-question replies are rendered and resolved natively (per question, on delivery). The real model behaved as the mock did: working → idle on every turn, across a tool call and a 25 s command, `agent read`, Ctrl+C (during the model phase; interrupting a running command is unverified) and `resume --remote`. Its two new breaks are in the launch and resume arguments, not the terminal (rows 2 and 6). |
| 2 | Server ownership | **One app-server per Codex worker, started from the worker's own pane** after fish and direnv have run, then the TUI in that pane (`setsid -f fish -c 'codex app-server --listen unix://SOCK'`). The CODEX_HOME daemon is never used: it runs every thread's tools and MCP children in the environment of whoever started it, and plain `codex` already auto-starts it (`daemon_auto_start`). Starting from the same pane is also what routes Herdr's session-id hook, which runs in the server, to the right pane. A new worker cwd must be trusted before the TUI starts: Codex's "Trust this folder?" dialog shows even with `--dangerously-bypass-approvals-and-sandbox`, and `agent start` then fails with `agent_not_ready`. Hire keeps its trust handling, or the server gets an in-memory override for that one cwd (`codex app-server -c 'projects={"<cwd>"={trust_level="trusted"}}' …`, which leaves `config.toml` alone). A launcher never sends Esc or Ctrl+C to a dialog it did not expect: on this one they open Codex's Agent command center, which lists every thread of the server's CODEX_HOME. |
| 3 | Lifetime | The bridge owns each worker's server: it records socket and pid and stops the server on send-home, fire and floor sleep (it outlives its pane and `herdr session stop`). It reports a dead server, which Herdr shows as `working`. |
| 4 | Subscriptions | `thread/resume {threadId}` without overrides, only while watching; `thread/unsubscribe` after. The thread id comes from Herdr's `agent_session`; ephemeral side threads are skipped. Herdr clears that value when the TUI exits and, after a resume, reports it again only with the first turn, so the bridge keeps the id it last saw and never reads a missing one as a new thread. |
| 5 | Approvals | The bridge stays passive and never answers a server request: the first answer wins. |
| 6 | Resume | Herdr's own resume drops `--remote` and the workspace env. herdr-3d resumes shared-mode Codex workers itself: server first, then `codex resume ID --remote … -C …` with hire's model args **minus `--dangerously-bypass-approvals-and-sandbox`**. A remote resume refuses any permission override ("Permission overrides are not supported when resuming a remote task"), Codex exits, and `agent start` only reports `timeout` after its full timeout. The thread keeps the permissions it was started with; `-m` and `-c model_reasoning_effort=…` are accepted. A restarted server needs the cwd's trust again: the in-memory override is per server (row 2). How to keep Herdr's native resume off such a pane is phase 2's first check. |
| 7 | Questions | Reply with the native envelope: `turn/steer` (with `expectedTurnId`) during the asking turn, `turn/start` after it. The terminal can no longer answer once that turn has ended, and Herdr shows a pending question as `blocked`. The server does not deduplicate, so the bridge must. |
| 8 | Terminal-free mode | Documentation only: a separate, persisted Settings opt-in with its gaps (no Herdr agent control, no TUI commands, the bridge answering approvals). The terminal stays the default. |

## 2026-10-06 — #155 (phase 2): Codex workers and the bridge on one local app-server

Built on #154's decisions (rows 1–8 above). Protocol: [Shared Codex server](../protocol.md#shared-codex-server). Code:
`internal/codexapp` (adapter, launcher, process ownership, checks), `internal/server/codexserver.go` and
`codexfloor.go`, four new `herdr.Control` shapes. Evidence (raw captures recorded during #154/#158, not published; regenerate with
`make codex-shared-tui EVIDENCE=<dir>`; conclusions in `docs/research/codex-shared-tui.md`):
`TestCodexShareResumeSuppression`, `TestCodexShareSharedLaunch`, `TestCodexShareSharedApprovals` (mock model) and
`TestCodexShareRealModelSmoke` (real model). Codex 0.160.1, Herdr 0.9.0.

| # | Question | Decision |
|---|---|---|
| 1 | Step 0: how to keep Herdr's own resume off a shared pane (D5) | **The TUI's own exit before the session stops.** `herdr pane release-agent <pane> --source herdr:codex --agent codex`, with the TUI running, changed nothing: the pane kept its `agent_session`, `session.json` kept the id and Herdr resumed the pane its own way on the next start. Leaving the session unreported is not possible: Herdr's SessionStart hook reports it by itself. After the TUI's exit the pane has no `agent_session`, `session.json` does not name the thread and nothing is resumed (`TestCodexShareResumeSuppression`: `rel`/`ex`/`ctl`). So the bridge's sleep quits each shared TUI (`/quit`, Enter: never Esc or Ctrl-C) and keeps the thread id itself. Not a different design from #154's: the documented fallback, minus the exit on wake, which stays as the safety net (a Codex Herdr resumed without `--remote` is quit, then relaunched). |
| 2 | The quit-to-stop race | Herdr forgets the pane's session **a moment after** the TUI quits; a `session stop` before that saves the id, and Herdr would then run a plain `codex resume` on wake, which starts the user's CODEX_HOME daemon (B2). The sleep waits (up to the send home's exit timeout) until the bridge sees no agent and no session on the pane, and notes it when it does not. The real-TUI suite caught this; the real-model smoke refuses to restart the session if `session.json` still names the thread. |
| 3 | Opt-in and modes (D8) | One bridge-wide switch, `codex_server.set`, off by default, persisted; Settings → "Codex workers". It applies to **new hires**. Each Codex hire made with it on records its launch (`codex_launch`: shared, or legacy and why), and keeps that mode: switching never touches a running worker. A Codex hire made with the switch off writes **no** record and runs byte-for-byte as before (legacy launch, Herdr's own resume, the sleep backfill). |
| 4 | Launcher (D1, B2, B3, B10) | From the worker's pane after its shell is up: the bridge writes `<--codex-run>/<marker hex>.fish` (0600 in a 0700 directory) and types `setsid -f fish <launcher> …` (`pane run`). The launcher marks the server's processes with a per-launch random token (`H3D_CODEX_SERVER`), records its pid and runs `codex app-server -c 'projects={"<dir>"={trust_level="trusted"}}' --listen unix://<socket>`: the directory trusted in memory (no "Trust this folder?" in a fresh directory with the real model; `config.toml` unchanged). Then the socket must answer with a supported server and the TUI is `agent start … -- --remote unix://<socket> -C <dir> -m … -c model_reasoning_effort=… --dangerously-bypass-approvals-and-sandbox`. The only shell-typed variable is the launcher path, under `CodexRun` and of plain characters; `-C` takes plain paths only. |
| 5 | Failures stay usable (acceptance 5) | Before the TUI: an unsupported `codex --version` (outside 0.160.x) or `userAgent`, a blocked or denied `.envrc` (`direnv status --json`), a path the launch cannot pass, a server that does not answer in 20 s: whatever started is stopped and the worker starts **the usual way**, the reason in the hire's ack (`codex.note`), its toast and the laptop's seat bar. A TUI that does not attach stops the server and falls back when the pane is at its shell, else the hire fails and rolls back. Codex's "Hooks need review" dialog (B8) is left to the player (answering it trusts hooks for every thread of the CODEX_HOME); the hire's first prompt is then not sent and says so. |
| 6 | Ownership and lifetime (D2, B5, B6) | The bridge owns the server: send home stops it after the agent exited, the sleep stops it after the TUI quit, a failed hire stops it. "Stopping" signals only this user's processes whose environment carries the launch's token (SIGTERM, SIGKILL after 2 s), then removes the launcher, socket (and the socket Codex may link it to), pid file and log. A dead server (pid gone, or another process under that pid: the start time is recorded) is `server: "down"` on the worker and on the seat bar, checked every 3 s; sleeping and waking the floor starts it again. |
| 7 | Resume (D5, B4, B9) | herdr-3d resumes shared workers on wake, alongside Herdr's own resumes: the pane at its shell, the server started again (a fresh token, the trust again), then `agent start <name> … -- resume <thread> --remote … -C … -m … -c model_reasoning_effort=…` without the bypass flag. Real model: 4.1 s, the history shown, the next turn ran and Herdr reported the same thread. The worker's `resume` is `fallback` ("relaunched"). |
| 8 | Thread identity (D3) | The thread is Herdr's `agent_session` for the pane, kept in the bridge's record: an empty value (the TUI exited, or a resume before its first turn) changes nothing, a new one is taken (a `/new` in the terminal), one that is another worker's thread is refused. The bridge never picks a thread among the loaded ones. Two workers in one session: two servers, two threads, never swapped (`TestCodexShareSharedLaunch`). |
| 9 | Worker-stop vs client-detach | **Worker stop** (send home, sleep) ends the server and everything it runs. **Client detach** (the transcript closed, the bridge reconnecting or gone) is `thread/unsubscribe` and closing the bridge's own connection: the terminal's subscription and the turn in flight go on (`TestCodexShareSharedLaunch`: a terminal turn after the bridge left). |
| 10 | The bridge's join and approvals (D3, D4) | `codexapp.Watcher` joins while the worker's transcript is open: `initialize` as `herdr_3d` (experimental API on, the `userAgent` version checked), `thread/resume {threadId}` with nothing else, `thread/unsubscribe` on leaving, reconnecting with a bounded backoff (0.25 s doubling to 5 s, 8 attempts in a row). It has no way to answer a server request: approvals and blocking questions are observed (`serverRequest/resolved`) and left to the terminal (`TestCodexShareSharedApprovals`: the modal stayed open until the terminal's `y`). Joining made no model request (mock) and started no turn (real model). The join also brings `thread/goal/cleared`, `account/updated` and `thread/tokenUsage/updated` notifications: the server's state for a new client, not changes the join made. This phase stops at the join and its events; questions and answers are phases 3–4. Rollouts stay under `~/.codex/sessions` (D6): the transcript tail is unchanged. |
| 11 | Orchestrator-created workers (D7) | Unchanged in this ticket: they start through the Herdr CLI and stay embedded. The procedure is the same two calls the bridge makes (`pane run <pane> '<server start>'`, then `agent start … -- --remote unix://<socket> -C <dir> …`); a shared helper on PATH that also checks direnv is the way the write-code skill adopts it. |
| 12 | Review round 1: send home never Ctrl-C's a shared worker (R1) | A shared worker whose terminal does not quit after `/quit` and Enter (up to three more) is **left as it is**: the send home fails ("no Ctrl-C to its shared Codex terminal … quit it there and send it home again"), nothing is closed and its server keeps running. Legacy workers keep the two Ctrl-C. Rejected: stopping the server instead, since a TUI whose server is gone does not exit but waits to reconnect (B6); reading the screen for a state where Ctrl-C is safe, since the only such state (an idle composer) is one `/quit` already handles. |
| 13 | Review round 1: wake without a thread (R2) | A shared worker that slept before Herdr reported its thread (Codex's hooks review, or no turn yet) is relaunched on wake like the others: its server, then a **new** TUI attached to it (`agent start … -- --remote … -C …`, hire's arguments). No thread is resumed or guessed. |
| 14 | Review round 1: wake without its server (R4) | When the server does not start on wake (an unsupported version, no answer, no run directory) or the terminal does not attach and the pane is at its shell, the worker resumes its thread on Codex's **embedded** server with hire's arguments: `agent start … -- resume <thread> -m … -c model_reasoning_effort=… --dangerously-bypass-approvals-and-sandbox` (new shape `resume-codex-embedded`; any `-c` keeps a plain Codex off the CODEX_HOME daemon, B2; the bypass flag is refused only by a *remote* resume, B9). Mock model, real TUI (`TestCodexShareSharedLaunch`, "wake without its server"): the shape resumed the thread with its history, the next turn ran, Herdr reported the same thread, no `app-server-daemon` was started, and Codex's own startup warning confirms B2: "Running without the shared background server: command-line configuration overrides (-c …) requires embedded mode". Without a thread it starts the way a legacy hire does. An embedded Codex may show "Trust this folder?" (no in-memory override there): it is answered as a hire answers it. **The worker stays shared**, with the reason as its note and `server: "stopped"` (the seat bar: "No own Codex server this time … the next wake tries its own again"): flipping it to legacy would hand its next wake to Herdr's own argument-free `codex resume`, which joins the daemon. Its next sleep quits the TUI as for any shared worker, and its next wake tries its server again. |
| 15 | Review round 1: a failed join is kept (R3) | A join that failed (its retries spent, or refused for good: ephemeral, another thread, an unsupported server) stays failed for that thread on that server (the launch's token): not tried again on the next tick. Closing and reopening the worker's transcript, another thread, or a new server (a wake, a relaunch) try again. Events are tied to the join that sent them, so a join that was left can no longer mark its successor detached. |

## 2026-10-06 — #156 (phase 3): Codex async questions and the bridge's answers

Built on #154 (findings §1, §2) and #155 (rows 8–10, 15). Protocol: [Codex async questions](../protocol.md#codex-async-questions).
Code: `internal/codexapp/questions.go` (the reconciler), `reply.go` (the envelope, moved from the fixture, and its
parser), `watch.go` (the join's history, `Steer`/`StartTurn`), `internal/server/codexquestions.go`. Evidence:
`TestCodexShareAsyncAnswers` (captures not published; findings §11; mock model, real TUI). Codex 0.160.1.

| # | Question | Decision |
|---|---|---|
| 1 | Seeing a question while the transcript is closed (D3) | **The bridge joins every shared worker's thread while its server runs and its thread is known**, transcript open or not (amends #155 row 10). Joining is passive and cheap: no model request, no turn, no setting changed (`Lifecycle/join-settings`, and the real model in #155). The join is also the only way to *answer* and the only source of the running turn the steer needs, and a prompt to a worker herdr shows `blocked` needs it attached the moment the prompt comes (row 10). Rejected: reading the rollout's `event_msg/item_completed` (`internal/transcript/codex.go` keeps hiding it), a second source with its own deduplication that enables nothing the join cannot; and joining on demand when a question is seen, which leaves the prompt refused for the seconds the join takes. |
| 2 | Failed joins (amends #155 row 15) | A join refused for good (ephemeral thread, another thread, an unsupported server) is kept as before: tried again when the transcript is opened, the thread changes or the server is new. One that only spent its retries (8, backoff to 5 s) is also tried again after 60 s (`CodexRejoin`): with the join no longer tied to the transcript, nothing else would ever retry a worker whose transcript is never opened. |
| 3 | Batch identity | A batch is an `agentMessage` with `delivery: "async"` and `questions`; its id is the function `call_id`, equal live, in `thread/resume` and `thread/read` history and after a cold resume (§2 [R]; `AsyncAnswers/30-d-hydrated`). The bridge never assumes it: live and history that disagree stay explicit. `twin`: two ids, same turn, same questions, each seen only one way (both kept and answerable); `conflict`: one id with different questions (the first kept, not answerable). Neither was observed. |
| 4 | Recovery | Every (re)join reconciles the history with what the bridge knew: the turns `thread/resume` returns, plus one page of up to 50 older turns (`thread/turns/list`, `itemsView: full`) when the response has a `turnsBackwardsCursor` (a paginated thread, `Lifecycle/16-cold-resume`). Older batches are not recovered (bounded joins). Batches first, then envelopes, so an answer never waits on its batch; an envelope for a batch not seen yet is kept (64 at most). |
| 5 | States | Per question: `pending`, `sending` (on the input lane, request in flight), `sent` (the server accepted it), `answered` (a user message whose whole text is the reply envelope naming `(call_id, index)`, live or in the history: the one rule for the bridge's and the terminal's answers), `dismissed` (the bridge only). The tool's `{"accepted":true}`, the turn ending and other user messages change nothing (§1 [R], `TestAsyncQuestionSurvivesTheAcknowledgement`). Kept per worker and thread in the hub, not in the join: a reconnect, sleep and wake keep them; a new thread (`/new`) and send home drop them. A bridge restart keeps only what the history shows (`answered`). At most 32 batches per thread. |
| 6 | Who answered | The bridge's sends carry `clientUserMessageId: "herdr_3d-<24 hex>"`; Codex echoes it as the user message's `clientId`, live and in the history (`AsyncAnswers/09-*`, `30-d-hydrated`: `by: bridge` from the history alone). `answered_by` is `bridge` for that prefix and `other` for anything else (the terminal's uuid, a client that names none). That is a proven pairing and it survives a restart; nothing else is inferred. |
| 7 | The answer command | `worker.answer_async {id, thread, batch, answers}`: checked when it arrives, queued on the worker's input lane (the one `worker.prompt` and `worker.keys` use), and checked again there in one hub step that also marks the questions `sending`: any other submission for them made before that step is `stale` from then on, whatever comes of the first (a generation captured when it arrives, `Questions.Admit`/`BeginAdmitted`; `TestAsyncAnswerSerializedOnTheLane`, `TestAsyncAnswerQueuedTwiceIsNotARetry`). The bridge must be attached (`invalid_state` otherwise: never queued blind). A question with options takes one of them exactly; one without takes any non-blank text. Whether the terminal accepts free text on a question that has options is unverified, so the bridge is strict. |
| 8 | Steer or start, and the completion race | A running turn (as the join last saw it): `turn/steer` with `expectedTurnId`; none: `turn/start` with the input only. The server refuses a steer that cannot land with nothing delivered: "no active turn to steer" and "expected active turn id … but found …" (`-32600`, `AsyncAnswers/12-*`, `13-*`). Any such refusal (a JSON-RPC error response) falls back to `turn/start` **once**. A `turn/start` while a turn runs is accepted into that turn and returns its id (`14-*`, `15-*`), so the fallback never opens a second delivery path. No response (a lost connection, a timeout) is `sent` with `unconfirmed`, never re-sent: the server does not deduplicate (§2). A refused `turn/start` is `input_failed`, the question `pending` with the reason. |
| 9 | The race phase 1 left open: steer accepted, then the turn ends first | **Dropped.** A steered input becomes a user message only when Codex delivers it with the next model request (`07-*` none before, `09-*` at delivery). Interrupted before that request, the turn ends `interrupted`, no user message is recorded, nothing reaches the model and the next turn does not carry it (`AsyncAnswers/18-*` to `27-*`); the terminal's badge goes with the turn. Encoded as `sent` + **`undelivered`** (set when the turn the answer reached ends without its user message, live or in the history): never re-sent by itself, and the user may answer it again (`28-*`: the second send is answered): only a submission made after it went undelivered; a duplicate queued before is `stale` (row 7), not a retry. This is what a fresh join already shows (`pending`: no envelope in the history). |
| 10 | Prompts stay usable (B7) | herdr refuses `agent prompt` while Codex's async question shows the worker `blocked`. A `worker.prompt` to a shared worker that is blocked, attached, with a running turn that asked a question still not answered, and **no server request open**, is steered into that turn (as Codex's own composer queues a message during a turn), with the same one fallback; ack `queued: true, via: "app_server"`. An open approval or blocking question is a real block: refused as before. Such a worker's screen is not read as a `question`. The legacy blocking ask is unchanged: `request_user_input_async` is not `request_user_input` (`TestAskTrackerIgnoresCodexAsyncQuestions`), and `internal/transcript/ask.go` and `internal/server/ask.go` are untouched. A terminal-only built-in still has to be typed into the terminal, so it stays refused. |
| 11 | What phase 4 (#157) consumes | `worker.codex.thread`, `.turn`, `.questions` (batches with `seen`, `twin`, `conflict`, `at`; questions with `state`, `answer`, `answered_by`, `unconfirmed`, `undelivered`, `error`, `truncated`), `worker.answer_async` (ack `sent` / `via` / `fallback` / `unconfirmed`) and `worker.dismiss_async`; the TypeScript types are in `game/src/net/protocol.ts`. The game's cards, and how a blocked worker with only async questions counts, are #157's. |

## 2026-10-06 — #157 (phase 4): answerable Codex async question cards in the transcript

Built on #156 (row 11: what phase 4 consumes) and the findings of §1 and §11 (docs/research/codex-shared-tui.md).
Protocol: [Codex async questions](../protocol.md#codex-async-questions) (`async_blocked`). Code:
`internal/server/codexserver.go` (`codexWorkerView`), `game/src/world/codexQuestions.ts` (the rules, pure),
`game/src/laptop/asyncCard.ts` and `asyncDrafts.ts` (the card and its drafts), `game/tools/fixture-codex-questions.ts`.

| # | Question | Decision |
|---|---|---|
| 1 | Telling an async question's `blocked` from a real one | **The bridge says so: `worker.codex.async_blocked`**, its `asyncBlocked` predicate (attached, the running turn asked a question Codex still holds, no server request open), the one a prompt already takes the app-server on (#156 row 10). The game cannot derive it: open server requests (approvals, blocking questions) are not on the wire. It is part of the worker's `codex` view, so `refreshCodex` re-emits the worker on every flip (`TestAsyncBlockedFlagFollowsThePredicate`: a question, an approval opened and resolved, the envelope, the turn's end, the join lost). It does not read `status`; the game combines them. No other bridge behaviour changed. |
| 2 | How such a worker counts | **Working.** `effectiveStatus` (`status: "blocked"` with `async_blocked`) is the one rule: the store's display (so the counts, N's queue, the inbox, notifications, the HUD, the desk card and the crowd), the P overlay (`promptBlocker` lets the prompt go and `willQueue` says it is queued, as the bridge acks it), the crew lifecycle, and the seated transcript's status (no screen-question banner, the live cue keeps saying what it does). A real block (the flag false) is exactly as before. |
| 3 | The "has a question" cue | **How many questions want an answer**: `pending` (a refused one with `error` included) and `sent` + `undelivered` (dropped: only the user can send it again). Not `sending`, plain `sent` or `unconfirmed` (a reply of ours is on its way, or its fate is unknown and it is never sent again), not `answered`, not `dismissed`; a twin pair once. The desk card says "Codex asks N questions · answer at the laptop (E)" with the first question, its status chip still WORKING; the look-at bar has "asks N questions" in the working blue. |
| 4 | An inbox row? | **No.** The inbox is "needs you or done", and an async question does not need you: Codex works on and reads an answer whenever it comes (until its turn ends; after it, only the bridge can answer, §1). A row would either count as needs-you (wrong) or need a third kind of row and notification for something non-blocking. The cue is on the desk card and the look-at bar instead. |
| 5 | Activity while herdr says blocked | **Known limit, left as is**: the bridge composes `activity` only for `working` (activity.go), so the desk monitor shows the terminal's last lines instead of the activity card while an async question is open. The transcript's own cue is derived in the game from the effective status, so it keeps updating there. Changing the bridge's activity rule was out of #157's scope (one flag, nothing else). |
| 6 | The card | **Non-blocking**, modelled on the follow-up card: the prompt box stays on, the terminal is a click or Ctrl+Esc away. The ask card's family (stacked questions, key caps, the foot) in the working blue (`--tx-sun` re-pointed on `.tx-aq`): solid like the ask (Codex's own questions, not inferred), not the sun of "needs you". One batch open, the others folded to a line, oldest first; ← → walk every question across batches. A question with options takes one of them (the bridge is strict, #156 row 7), one without a text box. Picking or Enter never sends; Send or Ctrl/⌘+Enter sends the answered questions of the open batch, once while it is on its way (a per-batch in-flight set until the ack or the command's end: a dropped connection settles it as `disconnected`). That set is the card's only guard. **The bridge is the duplicate guard** (#156 row 7: it marks the questions `sending` on the input lane, and any other answer submitted before is `stale`), and the card draws what it is given: the store's latest `codex` once a frame (`codexSeen` skips an unchanged one), so it may never see `sending` or `sent` (a hidden tab draws no frames while its socket goes on, review round 2). A guard waiting for a step it may not be shown would keep a legitimate retry (not delivered again, `pending` after a restart) disabled for good; without one, a send acked before its step is drawn (about a frame) can go again, and its `stale` is said calmly ("Already sent, answered or hidden — nothing more went to Codex"), the answer kept, no error (`asyncCard.retry.test.ts`: real store, controller and view). A blocking ask hides it, and the screen question's digits, the ask's and the follow-up's keys go first. |
| 7 | What the card says | **Only what the bridge has seen** (§11): "Sent — Codex will read it with its next step" (accepted is not read), "Sent, not confirmed" (no resend offered), "Not delivered — the turn ended before Codex read it" (the answer kept, Send again), "Answered" / "Answered elsewhere" (`other` is any client but herdr-3d, not necessarily the terminal), a refusal in words with the answer kept. Hide calls `worker.dismiss_async`: "Hide these questions on this card. Codex still has them: nothing is sent to it", never cancel; a hidden one is listed again, read-only, on demand ("N hidden"), and dismissals are not kept in the game (after a bridge restart they show again, legitimately). A `conflict` batch, or any while the bridge is not joined, is read-only: "Answer in the terminal while it shows them". So is a question whose suggested answer came shortened (`truncated`, an option within a character of the bridge's 1000-byte cut): the bridge checks a reply against the whole option, which the game never saw. A batch answered while you looked stays until you clear it ("Clear"); one answered before is not shown. |
| 8 | Drafts | **Above the view** (`AsyncDrafts`, held by `TranscriptMode`; the terminal toggle and a re-seat remount the view): `Drafts('codex-async')` keyed by worker, thread, batch and index, so a refusal, a drop, an upsert, a reconnect's snapshot, standing up and the toggle keep them; a draft goes when its question is seen answered or the thread changes, never on a missing `codex`. ## 2026-10-16 — Codex compatibility preference and 0.163.0

Codex upgrades should not force a player who accepts compatibility risk to wait for another herdr-3d release. The
working model stays one Codex terminal managed inside Herdr, with the bridge following its conversation and tool
steps in the transcript.

- **Settings → Codex workers → Allow unverified Codex versions** is a separate, bridge-wide preference, off by
  default and stored in SQLite. It persists across bridge restarts and future upgrades. The UI names the risk:
  transcript updates or question replies may stop working on an untested release. Codex 0.163 is added to the
  verified set, so it does not need this opt-in.
- The same policy covers CLI preflight, the actual server's handshake on hire/wake, and thread connections.
  Changing it refreshes bridge connections; it does not relaunch terminals, servers or turns. Existing legacy
