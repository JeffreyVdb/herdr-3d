## 2026-10-15 — #57: Several bridges, switched from ⌘P

The helper tunnelled to the one host `-host` named. It now keeps a list of named bridges, Settings → Bridges edits it
and ⌘P → Switch bridge picks one. The ticket left two questions open; the rest of the decisions are its Proposal's.

| # | Question | Decision |
|---|---|---|
| 1 | "Online": standby tunnels or periodic probes? | **One supervised connection per bridge, all the time**: an ssh entry its own `Tunnel` ending at `<dir of -local-socket>/bridges/<id>-<n>.sock` (row 11) (the existing supervisor: backoff to 30 s, `/healthz` every 5 s, `ControlMaster=no`), a local entry its socket dialled directly and checked every 5 s. The palette and Settings read a cached state, never an ssh handshake, and a switch to a bridge that is up is instant. The price is one idle `ssh -N` per ssh bridge, a handful with a handful of bridges, and an unreachable one costs a failed ssh start per backoff step (30 s at most). Periodic short-lived probes would save the idle processes but make every switch a fresh handshake and the state up to a probe interval old; they stay the fallback if idle ssh turns out to be unwanted. |
| 2 | `h3d-helper -bridge <name>` for scripting? | **Not now**: the game switches through `/api/bridges`; a script can too (`curl` with the token header). |
| 3 | Where the list lives | **The helper**, `bridges.json` (0600, its directory 0700) next to the token: `<config>/h3d-helper/bridges.json` (`~/Library/Application Support/h3d-helper/` on the Mac), `-bridges-file` / `$H3D_HELPER_BRIDGES_FILE` for tests and repros. Not a bridge's (unreachable while it is down) nor the browser's (the helper acts on it). |
| 4 | `-host` once there is a list | **The file is the truth once it exists.** `-host` / `$H3D_HELPER_HOST` (with `-remote-socket`) seed a missing or empty list (the host, named after it, in use: an install from before #57 comes up as it was) and are ignored after that, with a warning naming the file when they name a host it does not have. Otherwise the LaunchAgent's variable would undo every switch at the next restart. |
| 5 | `-local-socket` | Kept, so an installed plist's `H3D_HELPER_LOCAL_SOCKET` still works: its **directory** anchors the tunnels' local ends, `<dir>/bridges/<id>-<n>.sock`. Ids are 10 hex digits and `<n>` is checked as six base-36 digits, so the Mac's `~/Library/Caches/h3d-helper/bridges/<id>-<n>.sock` stays far below the 103-byte limit; an add whose path would not fit is refused in words. |
| 6 | Discovery of a remote socket | It used to run once at start and stop the helper on failure. Now it runs in the bridge's own supervisor, with backoff and the error as that bridge's `last_error`: it never holds up the start or another bridge. |
| 7 | What a switch closes | **Every connection dialled to the old bridge**, not only `/ws`: the proxies' `http.Transport`s keep idle keep-alive connections, and one left open would carry the next `/logo` or `/whiteboard` request to the old bridge. A dial that finishes after the switch is closed and refused. |
| 8 | `GET /api/bridges` guard | `/api/open`'s, but an **absent** `Origin` passes on `GET` (as on `/logo`): a browser sends none on a same-origin `GET`. The `X-H3D-Token` header still makes it a request no other site can send. Changes need the `Origin`. |
| 9 | The per-bridge key scope at start | The game asks the helper which bridge is in use before the App reads any key (in parallel with the font load, 2.5 s at most; the helper answers from memory). When it does not answer, the id it last named (`h3d.bridges.active`) is used, so a draft never lands in another bridge's keys. The keys from before #57 move into the **first** bridge's namespace, once (`h3d.bridges.migrated`). |
| 10 | Removing the bridge in use | Refused by the helper (`409 in_use`) and by Settings (the button says why; it asks no one). The list is never empty while it has a bridge in use. |
| 11 | Editing a bridge's address | **A fresh tunnel on a socket of its own, at once**: each tunnel the helper starts ends at `<id>-<n>.sock`, `<n>` counting the tunnels of this helper run. Review round 1 found that one `<id>.sock` per bridge, with the new tunnel waiting for the old one to stop, was not enough: the new tunnel was in use (and dialled) before it waited, so a dial during the old ssh's shutdown (up to `KillGrace`) reached the **old** host; and a second edit cancelled the waiting one, whose wait ended at once, so a third tunnel could start while the first still held the path, and the first's cleanup then unlinked the third's socket. A path per tunnel removes the shared resource: a dial reaches the new tunnel or nothing, and an old tunnel's cleanup only ever removes its own socket. Sockets an earlier helper run left (killed before its tunnels cleaned up) are removed when the list starts, but only those nothing listens on (the connection is refused) and never a local bridge's own path: a name alone does not make a socket stale (review round 2 found a live local bridge's socket in the socket directory unlinked). Tests: `TestAddressEditNeverReachesTheOldHost`, `TestRapidAddressEditsKeepTheirSockets`, `TestStaleTunnelSocketsGo`, `TestStartupKeepsLiveSockets`. |
| 12 | Another tab switches | **The helper refuses a page's `/ws` for another bridge than its own, and the page reloads on the new one.** Review round 1: a switch reloaded only the tab that made it; another tab's `/ws` was closed, reconnected through the new bridge and applied its snapshot while its drafts, seats and overview stores kept the old bridge's scope (and wrote it). Relabelling is not enough, since the scope is chosen once at start, before the stores read their keys. The page's `/ws` names its bridge (`?bridge=<id>`, `none` with none); `BridgeSet.Dial` compares it with the bridge in use under its lock, the post-dial check and `activate` closing the old bridge's connections cover a switch during the dial, and the `/ws` transport keeps no idle connections, so every `/ws` is checked. The page learns of the switch from any list it gets (polls while Settings or the switch list is open) and, since a background tab polls nothing, by asking for the list whenever its connection drops; on a mismatch it reloads with "Switching to <name>…" (`followActiveBridge`). Chosen over checking `/api/bridges` before each reconnect alone: that leaves a window between the check and the dial; the helper's check has none. The HTTP routes (`/logo`, `/upload`, `/whiteboard`, `/screen/frame`, `/drops`) are scoped the same way (review round 2: a stale tab's whiteboard autosave reached the new bridge, which took its scene on a matching floor name and base version): their URLs derive from the `/ws` one and carry `bridge`; their guard refuses another bridge with `409 bridge_changed` before proxying and hands the expectation to `Dial` for a switch made after the check; and since these proxies keep idle connections, the proxied URL's host names the page's bridge, so a proxy's pool never hands a page of A a connection dialled for B. A route's `bridge_changed` sends the page to the same follow path (it asks for the list and reloads). Tests: `TestWSKeepsThePagesBridge`, `TestRoutesKeepThePagesBridge`, `TestStaleWhiteboardSaveIsRefused`, `net/bridgeFollow.test.ts`, `net/bridgeChanged.test.ts`, the e2e "a switch made in another tab" and "a request the helper refuses for a switch made elsewhere". |

## 2026-10-15 — #68: Bash is the default bridge shell, Fish an explicit option

v1.45.0 hardcoded `/bin/fish` for a floor's wake and `setsid -f fish <launcher>` (a `.fish` file) for the shared Codex
server, a host-specific assumption carried over from the research machine (`docs/research/herdr-followup.md` §2a): a
Bash-login host (Omarchy) had to install Fish just to wake a floor. This entry **supersedes** the Fish-only wording of
the [#155](codex-integration-and-profiles.md#2026-10-06--155-phase-2-codex-workers-and-the-bridge-on-one-local-app-server) rows 2 and 4 (and of the research notes); those rows stay as the record of what v1.45.0 did.

| # | Question | Decision |
|---|---|---|
| 1 | The policy's shape | **A two-value enum, not a command**: `--shell bash\|fish` / `HERDR_WORLD_SHELL` on the bridge, next to `--codex-run`, default `bash`, validated at startup (`internal/shell`). No arbitrary command, no per-floor setting. |
| 2 | What may select Fish | **Only the option.** `$SHELL` is never read, and neither an installed fish nor an inherited `SHELL=…/fish` changes anything. Bash stays the default on a host with fish. |
| 3 | Finding the shell | The policy's absolute path: `$PATH`, then `/usr/bin`, `/bin`, `/usr/local/bin` (a user systemd manager's `PATH` is short). Fish prefers `/bin/fish` so its wake argv stays byte-identical to v1.45.0's, and is typed as a bare `fish` for the launcher as before. A path typed into a pane must be plain characters. Resolved at startup; a missing shell is an error naming the option and both fixes. The cached path is checked again before every wake and launch (it still exists, is a regular file after symlinks, has an execute bit: `shell.Verify`), because the detached `setsid -f` of a launch discards its exit status and the bridge would wait for a socket that never appears: the same error is returned and nothing is dispatched if the shell vanishes later. **Never a silent switch** to the other shell. |
| 4 | Launcher naming | **`<marker hex>.sh` for bash, `.fish` for fish.** `.sh` because it is short (the 90-byte path rule and the 108-byte socket path leave little room) and conventional; it is always run as `<abs bash> <file>`, never as `sh`, so Bash syntax is safe. `Control` refuses a launcher of the other format than its policy; the placeholder rules (`[A-Za-z0-9._/-]`, in `CodexRun`) are unchanged. |
| 5 | Upgrade and recovery | **`Launch.Remove` deletes the launcher of every shell's format** and `Write` replaces any. A stored launch has no shell (its record is unchanged): a `.fish` launch written by v1.45.0 is stopped, recovered and cleaned up by a bash-default bridge. A launch is only ever started afresh, never by re-running an old launcher. |
| 6 | The Bash launcher and wrappers | A non-interactive `bash script` reads no `~/.bashrc`, so a user's `codex` function or alias would be lost silently, where fish reads `config.fish` even then. The launcher therefore exports the marker, records `$$`, and **`exec`s an interactive bash** (`"$BASH" -i +H -c '<command>'`): `~/.bashrc` is read as in the pane (behind the `$- != *i*` guard), the pane's exports are inherited, no terminal is needed. Chosen over sourcing `~/.bashrc` from a script (the guard returns before the function) and over `bash -i <script>` (the pid file then holds a process whose own environment lacks the marker: exports of a running shell do not change `/proc/<pid>/environ`). Checked empirically under real bash with a `.bashrc` function and alias, and in a real throwaway herdr pane. |
| 7 | The pid contract | The pid file holds the launcher process, now the `exec`'d interactive bash: it stays the supervisor (a `codex` function runs as its child), leads its own session (`setsid`) and **its own environment carries `H3D_CODEX_SERVER`**. Ownership is still the marker scan (`MarkedPIDs`, `FindServer`, `Alive`): the supervisor's command line holds the quoted `--listen '…'`, so only the codex process is found as the server. `HISTFILE` is unset in the launch, so the user's history is never rewritten. |
| 8 | What Bash wrappers support | `codex` functions and aliases in `~/.bashrc` (also `command codex`). Not: a `.bashrc` that execs another shell or needs the terminal, and functions or aliases only a login file or prompt hook defines. Exported variables (direnv's, `PATH`, `HERDR_*`) always arrive. Documented in `docs/protocol.md` "Shell policy" and `CONTRIBUTING.md` "Bash and Fish hosts". |
| 9 | Unchanged | `CleanEnv`, argument validation, 0700/0600 permissions, ownership verification, "stop only that worker's server", `--working-directory`, `KillMode=process`, the unit name. |
| 10 | Tests | `TestControlAllowlist` runs both policies; real-bash launcher tests (`internal/codexapp`) cover the wrapper sentinel for function, alias and fish, the marker, pid, detached session, history, quoting and cleanup of both formats; the integration fixture takes `H3D_CODEXSHARE_SHELL` (bash default; fish skipped when absent). |
## 2026-10-19 — #116: direnv is a mise shim with no version selected

A Codex hire with the shared-server switch on fell back to Codex's built-in server with mise's whole multi-line diagnostic
as its note (`direnv status: direnv: exit status 1: mise ERROR No version is set for shim: direnv …`), shown as it was on
the seat bar and in the hire's toast. The investigation (`docs/research/codex-direnv-preflight.md`): the bridge's PATH is
shim-first, direnv is installed but no version is selected for the worker's directory, so the shim passes `exec.LookPath`
and then fails. The fallback itself stays (#18, #155, #186). Code: `ExecError`, `DirenvUnselectedError` and the
recognition in `Preflight.Check` (`internal/codexapp/preflight.go`), the Warn in `hireShared`
(`internal/server/codexserver.go`), `codexNotice` (`game/src/world/codexServer.ts`), the fixture's `simfail=codex_direnv`
(`game/tools/fixture-codex-server.ts`).

| # | Question | Decision |
|---|---|---|
| 1 | Missing, or present and unusable | **Not the same.** A direnv that is genuinely absent is still skipped (nothing to check). A shim that exists but cannot run is a refusal: the `.envrc` could not be validated, so it is neither "direnv missing" nor "no `.envrc`". Any other nonzero exit stays the generic `direnv status: …` refusal. |
| 2 | Recognition | The runner's failure is a typed `*ExecError{Name, Err, Stderr}` (its text exactly as before, `Unwrap` to the exec error, stderr kept to 4 KiB instead of 300 bytes). `Check` turns an `ExecError` whose stderr carries mise's `No version is set for shim: direnv` (or `mise which`'s `is not currently active`) into `*DirenvUnselectedError{Dir, Detail}`. Matching the text is the only signal mise gives: its exit code is 1 like any failure. |
| 3 | One line out, the detail kept | `Error()` is `direnv is installed through mise but has no version selected for <dir>`: that is the persisted note (`shared Codex server: …; started the usual way`) and the hire result. `Detail` is mise's stderr; `hireShared` logs it at Warn with the worker and the directory. The wake path runs no preflight (`startSharedServer` only), so it has no such note. |
| 4 | Laptop copy | `codexNotice` recognizes that one line (the same words on both sides, pinned by a test in each language) and says what it is, where to fix it (`docs/git-worktrees.md`) and what the worker is left with, and to send it home and hire a new one. No mise lines. Other reasons render as before. |
| 5 | Remedy | Documentation only (`docs/git-worktrees.md`): the bridge's environment and the worker's pane both need a selected direnv; per-worktree `mise.local.toml`, a bridge `Environment=MISE_DIRENV_VERSION=…`, or a global `mise use -g` as the host owner's choice. **The app never runs `mise use`, installs, trusts a config, writes `direnv.toml` or runs `direnv allow`**, and does not choose a version for the host. Rejected: probing `mise which` to pick a binary path (it would make the app choose a version policy, and a stale path breaks on upgrade). |
| 6 | An existing fallback hire | Persisted as `legacy`; it is never migrated, by a fix or by toggling the setting. Send it home and hire a new one (documented). |
| 7 | Tests | Through the real `ExecRunner` with executable `direnv` scripts in `t.TempDir()` (`TestPreflightRealRunner`: inactive shim, `mise which` wording, other failure, no `.envrc`, allowed, blocked, denied, missing executable; `TestExecError`); `TestSharedCodexHireDirenvUnselected` (the exact note, the legacy launch, the usual start, the Warn); `ui/codexServerSection.dom.test.ts`, `ui/hiredToast.test.ts`, the fixture test and `e2e/h155-codex-server.spec.ts` (`simfail=codex_direnv`). |

## 2026-10-21 — #147: the bridge deflates its websocket (permessage-deflate, context takeover)

Every transcript's first-page ack (median 479 kB, largest 767 kB over the 64 private #126 acks), the start-up snapshot
and every reconnect crossed the SSH tunnel uncompressed: the bridge accepted websockets with nil options, and
coder/websocket's default is no compression. Code: `acceptOptions` (`internal/server/ws.go`); tests
`internal/server/compress_test.go`, `TestWSCompression` (`internal/helper/server_test.go`); benchmarks
`internal/server/compress_bench_test.go`.

| # | Question | Decision |
|---|---|---|
| 1 | Mode | **`websocket.CompressionContextTakeover`**, the library's superset: a client that offers only `client/server_no_context_takeover` gets that, one that offers nothing gets no compression. Chrome (the Mac's `--app` window) offers `permessage-deflate; client_max_window_bits` and gets context takeover both ways; the library's "Safari does not implement it" note does not apply. Go clients (`proto.Dial`, the codex-shared-bridge suite) dial with default options, offer nothing and are unchanged. The helper's proxy forwards the offer and the answer as they are (`Sec-WebSocket-Extensions` is end to end; `TestWSCompression` pins it). |
| 2 | Threshold | **The library's default, 128 B** (no `CompressionThreshold`). The writer level is fixed at `flate.BestSpeed` (the ticket's level-6 figure is not reachable). Over a burst of `worker.status` events (225 B each) context takeover sends **27 B** a message at 7.8–8.5 µs (0.73–0.75 µs uncompressed); a threshold of 512 or 1024 leaves them at 229 B. A watched transcript's live tail (each item of the median ack in a push of its own, 572 B mean): 158 B at 13–16 µs with 128, 286 B at 8–9 µs with 512, 297 B at 8–9 µs with 1024, 334 B at 7 µs without context takeover, 576 B at 0.5 µs off. At the bridge's message rates that is well under a millisecond of CPU a second per page, so the smaller messages are worth it where they come in bursts. |
| 3 | Measured: acks (`BenchmarkDeflateAcks`, the 64 dumps as `transcript.watch` acks, Chrome's offer, bytes the bridge writes) | **30.23 MB → 8.37 MB (3.61×)**; median ack 478.6 → **134.1 kB**, largest 767.2 → **203.6 kB**. Without context takeover 8.39 MB (3.60×): on big messages the two modes are the same, the window pays on small ones (row 2). |
| 4 | Measured: CPU per ack (`BenchmarkDeflateAckWrite`, the bridge's `ws.Write` on a connection that drops what it is given, this host, i7-10750H at load 6–7) | Median ack **4.8–5.0 ms**, largest **7.5–8.2 ms** (≈ 95–103 MB/s), 0 allocs/op (5–10 kB/op amortized from the library's pools). Uncompressed the write is under 1 µs there (no copy). The write runs on the connection's own writer goroutine (`serveWS`), not on the hub's. |
| 5 | Memory | Per connection that negotiated it: the `flate.Writer` (BestSpeed: **486 kB** measured on Go 1.27; the library's comment says 1.2 MB), made at the first compressed message (the snapshot) and kept for the connection's life, plus a 32 kB window for the client's own deflated messages and a pooled 45 kB reader while reading one. **About 0.5 MB per open page**; the bridge holds one websocket per open page (a page or two on the Mac), and Go clients negotiate nothing. |
| 6 | Read limit | `ws.SetReadLimit(maxClientMsg)` bounds a client's message as inflated (the limit reader wraps the flate reader), so a small deflated message that inflates past 256 KiB is still refused with "message too big" (`TestWebSocketCompressedReadLimit`). |
| 7 | The real browser | Chromium 149 (Playwright) through the helper's own handler (`helper.NewServer`, its `/ws` proxy and checks) on 127.0.0.1, the bridge on a local socket (no SSH tunnel), a page that says hello and reads the snapshot of a floor of 2000 workers: CDP `Network.webSocketHandshakeResponseReceived` shows `Sec-WebSocket-Extensions: permessage-deflate`; the 833.8 kB snapshot arrived whole, and the helper wrote **133.4 kB** on the browser's connection (834.1 kB on the base commit, which negotiates nothing). CDP's `webSocketFrameReceived` shows the inflated payload, so it cannot measure the wire. |
| 8 | Not measured | **The end-to-end saving over the real SSH tunnel is still an estimate** (the ticket's 40–90 ms per open from fewer slow-start round trips at 23 ms RTT, more on a thin uplink). To be confirmed on the Mac after deploy: `transcript.watch` → ack time, before and after. |

## 2026-10-23 — #196: the MCP & skills wall reads configuration passively and starts servers only on request

The wall screen and its overview show, per harness, the MCP servers and skills configured for a floor's checkout and
Codex profile. The bridge part: `internal/mcpinv` (the reads, the checks and their cache), `internal/server/mcp.go`

exported, wired into `mcpinv` by the app as its `Runner`: the hub reaches no harness package,
`TestCommandCatalogIsProviderNeutral`), the `expected_mcp` floor setting; protocol: [MCP and skills](../protocol.md#mcp-and-skills); research:
`docs/research/mcp-skills-wall-display.md`.

| # | Question | Decision |
|---|---|---|
| 1 | Passive vs active | **An inventory read starts no MCP server and sends no turn**: Claude Code's config files and SKILL.md folders are read by the bridge itself (no process); Codex's are a fresh app-server's `config/read` and `skills/list` (they start no server). Starting servers is a **connection check**, only on `mcp.check`, never on a timer or on view; Codex's no-thread `mcpServerStatus/list` starts every enabled server on each page, so it is a check, never a read. |
| 2 | Unapproved project servers in the Claude check | Headless `claude -p` starts a project's `.mcp.json` servers without asking. The check passes every server not approved (pending and rejected) as `disabledMcpjsonServers` in `--settings`. Measured on 2.1.309 with an isolated `CLAUDE_CONFIG_DIR` and fake servers: with the list an unapproved server never started; without it, it did; the `.mcp.json` of every folder above the checkout is loaded too, past the git root (the closest definition of a name wins), and the list excludes those as well. So the reader and the exclusion walk every ancestor to `/`, and a check is `skipped` when one of those files cannot be read. The `skipped` fallback for "the setting is ignored" was not needed. |
| 3 | Cache identity | `(harness, cwd, config home)`: Claude Code's config dir; Codex's resolved `CODEX_HOME` (the default profile runs without one, as a default worker does). A profile's answer is never another's. A separate cache from `harness.Catalog`, the same stale-while-revalidate shape, plus backoff (30 s doubling to 5 min), a 10 s first-read wait then `pending`, 64 keys. |
| 4 | User scope | Processes for user scope (no checkout) run in an empty private temporary folder: the bridge's home could hold a `.mcp.json` or a `.codex/` project layer. That folder still has folders above it (Claude Code loads their `.mcp.json` too, review round 1), so a user-scope Claude check also passes every `.mcp.json` server of those folders and of `~/.mcp.json` as `disabledMcpjsonServers`, approved or not; a folder free of them was not chosen because `/` or the home folder can hold one. |
| 5 | Audit | `mcp.inventory` is not audited (polled, reads configuration; also when refused), like `host.watch`; `mcp.check` is (it starts processes). |
| 6 | Worker observations | Only attached shared-server Codex workers of the floor in the asked checkout and profile, through their own thread **and a named server** (`threadId` plus `serverName`), at most once per 30 s each and only while `mcp.inventory` is asked. Correction, 2026-10-25: a bare thread id still creates fresh connections on Codex 0.163.0. Names come from passive `config/read`; the real remote-TUI regression `TestCodexShareMCPStartup` verifies that named reads reuse the connection (also passed on 0.160.1). Claude workers have no control connection: their live status is not shown. |
| 7 | Display safety | By construction: the wire types have no field for commands, args, env, headers or URLs (a Claude server's command, args, URL and headers are decoded only to match the MCP policy, row 11, never copied out), and every note or reason is a bridge phrase (error text is reduced to a category). Tests marshal fixtures with secret-shaped values and assert none reaches a Snapshot. |
| 8 | Claude skills | Disk discovery of `<root>/<name>/SKILL.md` only (managed, user, project up to the repository root, enabled plugins), `complete: false`: no control request lists skills with their origin without reloading them (`reload_skills` is a state change). |
| 9 | Approval precedence (review round 1) | Measured with `get_settings` on 2.1.309: `enabledMcpjsonServers` and `disabledMcpjsonServers` add up over the scopes; `enableAllProjectMcpServers` is the most specific scope's (managed, `settings.local.json`, the `~/.claude.json` project entry only when `true`, project `settings.json`, user), so a local `false` revokes a user `true` (it was OR-ed, so the check started a server the user had revoked). `get_settings` does not show trust: per the docs the project's two files approve only in a trusted folder, so there they may only take approvals away (fewer approvals: the check never starts more). A matrix test covers every combination. |
| 10 | Failed reads (review round 1) | A failed state without an error (a refused RPC) and a Claude read that turns `partial` after an `ok` one are failures: the half keeps its last good rows, stale, and backs off. A `partial` read with nothing better kept is shown as it is and is no failure, else a lasting unreadable plugin manifest would freeze the half forever. |
| 11 | MCP policy (review round 1) | `deniedMcpServers` / `allowedMcpServers` / `allowManagedMcpServersOnly` and `managedMcpServers` follow managed-mcp.md: name, command line and URL pattern entries, deny first, the organization's servers need no allowlist entry. `${VAR}` values are not expanded (the policy's pinned environment is not the bridge's), so they never make a server `blocked`. | 12 | Bounds (review round 1) | 64 keys including those in flight, 4 reads and checks at once: past them a request starts nothing (`pending`, or a `skipped` check not recorded) instead of queueing, since the client polls anyway. The checks of the last 30 s are kept apart from the evictable keys (at most 64), so eviction does not reset the cooldown. The Claude check's 20 s bounds the process too (it had 3 s more). |
| 13 | The overview's backdrop | The MCP & skills overview holds the typed expected-server list, so it is a `none` dialog (only its close button and Esc), listed in #51's table and in CONTRIBUTING. |
