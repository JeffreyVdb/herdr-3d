## 2026-10-07 — #174: reasoning effort and a real completion budget for the floor overview summaries

The overview's TASK lines stayed at "Please investigate." with summaries on, a ready LLM and budget left. Two causes: `max_tokens` was a hardcoded 80, which a reasoning model (`openai/gpt-6-luna` through OpenRouter) spends entirely on thinking, answering HTTP 200 with empty content and `finish_reason: "length"` (the audit said `bad_response`, 0 answer bytes); and a failed task call was never asked again (`taskTried` was set before the call and only a busy, not-ready or capped outcome cleared it). Research on what providers accept: `docs/protocol.md` "Floor overview summaries"; sources there and in the ticket.
Code: `internal/ai/{reasoning,openai,service}.go`, `internal/digest/{digest,service}.go`, `internal/server/digest.go`, `internal/store/digest.go`, `internal/transcript/digest.go`, `game/src/ui/{digestSection,overview}.ts`, `game/src/world/{digestSettings,overview}.ts`.

| # | Question | Decision |
|---|---|---|
| 1 | Where the two settings live | **On the summaries feature, not the shared LLM config**: `digest_settings.reasoning_effort` (`""` = provider default, nothing sent) and `max_tokens` (0 = the default), SQLite. The LLM role's `ai.json` and `extra_body` are untouched, so the follow-up questions (1200), pack up (600) and classification (64) keep their own `MaxTokens` and send no effort; the effort is a field of `ai.Request`, data on the request, never a vendor client in `digest` (`TestDigestUsesOnlyAIInterfaces`, `TestAIIsFeatureAgnostic` hold). The UI says so under the two controls. |
| 2 | The default budget | **1,024** (range 64–16,384), up from 80, shown as "In use". It is the provider's generation budget **including reasoning**, not the line length (task 80, now 100 characters, unchanged). 1,024 is not a guarantee with reasoning left on (OpenRouter documents no universal minimum; OpenAI suggests far more when experimenting): a truncated call says so (#6) and the Test shows what each sample spent. Validated against a fake provider that spends 300 tokens thinking (`internal/digest/provider_test.go`): 80 tokens → truncated, 1,024 → both lines, effort `none` → fine even at 80. OpenRouter's unified `reasoning: {effort}` would be OpenRouter-only. Never an effort the list omits (Luna has no `minimal`). Other endpoints list ids only: `unknown`, the generic `low/medium/high` offered, any gateway effort accepted by the API, and a value the model refuses (HTTP 400 with an effort set) fails as a clear `bad_config`, never silently. A model known to have no reasoning gets no control (disabled, with the reason). A **saved** effort the model does not take is `effort_stale`: shown marked, **not sent**. The catalog entry is cached 30 minutes (2 minutes after a failed read) and read by `digest.get`/`digest.set`/summaries; no call at all without an effort chosen. |
| 5 | What the tested/ready fingerprint covers | The summaries test (`tested`) covers **the LLM's config (base URL, model, key, extra_body), the effort and the budget**: changing any needs a new test before switching on. The input-hash cache of lines is deliberately **not** keyed by them: a line written for an input is still the right line, and re-asking after every settings change would spend the cap. What a config change does invalidate is the failures (#7). |
| 6 | Telling a truncated answer from a malformed one | `ai` gets two kinds, `truncated` (the provider's `finish_reason` is `length`: always when there is no text, and for any text when the request says `NoPartial`, which the summaries do: a half line is never shown) and `empty_answer` (well-formed, no text); both were `bad_response`, now reserved for a malformed answer.
