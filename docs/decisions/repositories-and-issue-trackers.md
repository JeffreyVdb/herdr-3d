# Repositories and issue trackers decisions

## 2026-10-01 — #66: the main checkout herdr opens for a worktree hire

| # | Question | Decision |
|---|---|---|
| 1 | Show it, hide it, or avoid it? | **Hide it** (the issue's option 2). `herdr worktree create` opens a workspace for the repository's main checkout when none is open on the floor; it holds a shell, no agent, and the player expects one minion per hire. Option 1 needs a new prop, option 3 needs herdr. |
| 2 | When is a workspace hidden? | A **stateless rule** on herdr's current state (`world.HiddenMainCheckouts`): a repository's main checkout (`Worktree` set, not linked, `RepoRoot` set), no agent, and a linked worktree workspace of the repository open on the same floor. Nothing is stored, so it survives bridge restarts; an agent starting in it, or the last worktree going, makes it a worker again by itself (`worker.upsert`). A shell the user opened in a main checkout is hidden by the same rule while worktrees of it are open. |
| 3 | Capacity | A worktree hire is **one** worker. `mainCheckoutOpen`, `hireOp.extra` and the "counts two" check are gone; the hidden workspace is not in `f.order`, so `counts`, `deskCount` and the caps never see it. |
| 4 | Cleanup | Sending home the last worktree of a bridge-hired worker (a `hire_branch` record exists), or rolling a worktree hire back, closes the hidden main checkout with `workspace close` once no linked worktree of the repository is open, only while it still has no agent. `workspace close` kills every process in the workspace, so the hub's last observation is not trusted for that: immediately before each close it re-reads herdr (`session.snapshot`, an allowed read, `Options.Fresh`) and skips the close (logged and audited) if an agent runs in the workspace, a linked worktree of the repository is open again, the workspace is gone, or the state cannot be read. Best effort: a failure is logged and audited, the send home still succeeds, and the workspace then shows as a worker. The workspace stays hidden while the operation runs (`holdRepos`), so it never flashes between the worktree going and the close. |
| 5 | `can_fire: false` | Stays for a main checkout that is visible (one with an agent) while worktrees of it are open. |

## 2026-10-01 — #52: dragging issue cards between status columns

| # | Question | Decision |
|---|---|---|
| 1 | What order does a column have? | **The GitHub project's own item order (option A).** `ProjectV2.items(orderBy: {field: POSITION, direction: ASC})` (POSITION is the only field, and the default; the feed names it anyway) is one manual order across all statuses; filtered per Status it keeps its relative order, which is the column order of an unsorted board view on github.com. It survives restarts and other clients, and another client's reorder shows on the next poll. The bridge's SQLite (option B) would have drifted from GitHub's board; columns without an order (C) do not meet the issue. A view with its own sort shows GitHub's sort there, not this order: only unsorted views agree. |
| 2 | How it is read | In the feed itself: the project's first 100 items (their id, the Issue's node id, the Status option) cost no extra point in the spike's measurement (9 → 9); more are paged 100 at a time, at most 5 pages. Each card gets `position`, its 0-based rank among the cards (matched by the Issue's node id, never its number: another repository's issue may have it); drafts, pull requests, content out of reach and issues that are not cards are skipped but stay in the provider's full sequence (the top of a column needs it). Past the page limit no card has a position (never a partial order) and the board is `truncated`. The default `archivedStates` leaves archived items out, like the Status the feed already reads. |
| 3 | How the client sorts | `columnViews` sorts every column by `position`, done columns too; cards without one follow, by the old rule (urgency then recency; done: latest closed). A provider with no order sends no position and gets exactly the old sort. The 3D wall uses the same views, so it follows the order (it stays read-only). |
| 4 | Wire shape | **`issue.set_status` gets an optional `after`** (protocol v1, additive): absent is the old status-only write (the modal's Move to… and older clients); `null` is the top of the column; a card id is right after that card. Go tells absent from null with `proto.Optional`. It is validated like an id, must be another card of the target column on the last board, else `bad_request`. A new capability `order` (GitHub: with a project, like `set_status`) gates it: an `after` without it is `unsupported`. A board with `set_status` but no `order` still takes drops between columns, with a column highlight only and no `after`. The tracker interface: `SetStatus(ctx, id, column, *Anchor)`, nil for the status only. No GitHub id goes on the wire. |
| 5 | The GitHub writes | Resolve or add the project item (as before), then the Status write **only when it changes** (a reorder in the column writes the place only; without `after` the status is always written, as before), then `updateProjectV2ItemPosition {projectId, itemId, afterId}`. `afterId`: the anchor card's item; for the top of a non-empty column the item right before the column's first card in the global sequence, the moved item left out (none when that card is the project's first); for an empty column none (the top of the project). It is worked out before anything is written, from the last feed's order when nothing was written since, else from a fresh read of the items (about 1 point a page). A failed write after one that landed (the place after the status, the status after an add) says so ("its status changed, but its place in the column did not") and is a `provider.ErrPartial` besides its own kind: the bridge, which knows no provider, refreshes after it as after a success and drops the polls in flight, so the board shows GitHub's truth at once (fix round 2). An anchor that is no longer in the order is `stale`. Tests use fakes only; no mutation ran against the real project. |
| 6 | A drop into Done | **Changes the status only; the issue stays open**, the same as Move to… (closing is `issue.close`, with its confirmation and reason). Done sorts by position like every column. |
| 7 | A move right after a poll | Bridge: every successful write counts on the floor; a poll that began before the latest write is dropped when it lands (not sent, not cached) and the refresh runs instead. Before, a refresh asked for while a poll was in flight was lost (the poll's end set the next poll a minute later) and the in-flight poll's older board was shown. After a successful `issue.set_status` the bridge's last board also has the card in its new column, so a second drop anchored on it is valid before the refresh lands. Game: a drop shows at once; a failure puts it back and says `failureText('issue.set_status', …)` in the board itself, in a `role="alert"` line above the columns (a HUD toast would be under the modal board and outside its accessibility tree) until it is dismissed or the next drag starts; after a partial failure the refresh that follows shows the card's real column (the failed move is forgotten, so nothing holds it back); an acknowledged move holds until a non-initial `board.issues` that came after the ack shows it in that slot, or 20 s at most, so a stale board never makes the card jump back. Drops are sent one after the other (a drop may be anchored on the card the one before moved). |
| 8 | A poll during a drag | The overlay does not redraw the columns while a drag is live (the drag measures them); what came meanwhile is drawn when it ends. |
| 9 | Interaction | Pointer events (mouse, pen, touch), not HTML5 drag and drop (no touch). Mouse and pen: the drag starts after 5 px, so a click still opens the card (and the click after a drag is swallowed: a drag ended while the button is still down, by Esc or the columns going away, swallows the click of its release, however long that takes up to 10 s; a new press ends that early, and a keyboard click is never swallowed). Touch: a 380 ms long press, so a swipe on a card still scrolls the board; once live, a non-passive `touchmove` on the board stops the page from scrolling. The note lifts (tilted, a pinhole where its pin was) and follows the pointer; its old spot is a dashed ghost that keeps the pin; the column under the pointer lights up; the slot is a sun-yellow thread with a pin at each end, drawn above the note (the slot is usually under it), placed by each card's midpoint. Near the board's edges it scrolls (sideways and down). Esc, a drop outside a column, on "No status" (a source only) or on the card's own place, and a cancelled pointer send nothing. `prefers-reduced-motion`: no lift animation and no glide of the line; the line still shows. The modal's Move to… stays the keyboard and screen-reader path; a keyboard drag is not in this change. |

## 2026-10-07 — #184: Kaneo as a floor's issue tracker

A floor can take its issues from a project of a Kaneo instance instead of GitHub. The bridge-wide connection lives in
`internal/kaneoconf` (settings, the key's file, the test that gates a save, the generation); the server, the store and
the protocol never import the Kaneo client (`internal/kaneo`), which `app` wires in behind `kaneoconf.Connector` and
the board factory (`TestBoardLayerIsProviderNeutral`, `TestKaneoSettingsIsProviderNeutral`).

| # | Question | Decision |
|---|---|---|
| 1 | Default workspace semantics | The global default workspace is a **prefill** for a floor not linked yet. A floor's save stores its own explicit `(workspace_id, project_id)`; a later change of the default never rebinds it. Names are stored beside the ids for show only; ids are authoritative. |
| 2 | Save gating | The bridge, not the client, insists: `kaneo.set` saves only an instance and key that passed `kaneo.test` (the key by its SHA-256, in memory) within 30 minutes, and a default workspace that test listed. A test changes nothing saved; a failed save changes nothing. The panel's own gating (an edit undoes the test) mirrors it. |
| 3 | A key for another instance | A blank key means the saved key **only for the saved API base**; any other address without a typed key is `key_required` before a request goes out, so a saved key never travels to a different host, a test included. Same instance written as origin or `/api` base is the same instance. |
| 4 | Where the key lives | Its own `0600` file (`kaneo.json` next to the database, `--kaneo-file`), atomic like `ai.json`, apart from the AI integration (a Kaneo key is not an AI key; clearing one never touches the other). No key hint is shown (only `key_set`): the ticket asks for safe metadata, and the last four characters are not needed to recognise one Kaneo instance's key. |
| 5 | Generation | A counter persisted in the file that moves when the instance or the key changes, or on disconnect. Every Kaneo floor's board source names it, so the board, its SQLite cache and any poll in flight of an older generation are dropped (`finishPoll` re-runs `boardOf` before applying a result). A default-only change keeps it (the boards stay). |
| 6 | Runtime 401 | Kaneo's key verifier answers an exhausted quota with 401, so a 401 is never "the key is invalid". A poll's 401 pauses **every** Kaneo floor (one key, one quota) for 5 minutes through the provider's rate gate, marks the connection `paused` (a `kaneo.update`), and `board.refresh` does not poll meanwhile. It resumes on the cooldown's end, on a passing `kaneo.test` of the saved connection, or on a new connection. A 403 is `forbidden`, shown as a permission problem, with no pause. A command's 401 or 403 is reported as such and changes no state. |
| 7 | Floor saves that need Kaneo | `floor.settings.set` moved to the asynchronous command path: a save that stores a new link or switches to Kaneo asks Kaneo for the project (`GET /project/<id>`: it must exist, belong to the workspace and not be archived) off the hub goroutine, then applies the args again to the floor's current settings. Only the tracker and the link are compared, so a concurrent save of the floor's other settings does not make it stale. Saves that do not touch the link stay synchronous and call nothing. |
| 8 | Tracker and code host apart | `BoardSource` gained `Tracker` and the Kaneo fields (instance, generation, workspace, project; never the key). The inactive tracker's settings are kept in `floor_repo`. A Kaneo floor's pull requests read GitHub's rate gate, not Kaneo's. |
| 9 | Virtual columns | Kaneo's `planned` and `archived` are columns with `kind` (always present, `planned` first, `archived` last). Archive is not completion: only `done` columns (Kaneo's final ones; there can be several) make a card `closed`. The game draws the virtual ones as dashed trays with a note ("archived, not done") and never gives them the done chip. |
| 10 | Close | Off for Kaneo (`capabilities.close: false`, `issue.close` `unsupported`): no duplicate or not-planned reasons, no silently chosen final column, and never `DELETE /task`. Completion is a move to a final column. |
| 11 | Missing timestamps | Kaneo gives none: `updated_at: 0`, `closed_at: null`. The game shows no time and no "closed recently" (the seven-day window is GitHub's). |
| 12 | Truncated boards | A bounded read that stopped early is `truncated`, said on the board. A placed move on it would anchor to cards the bridge did not see: the game sends a status-only move there (the provider refuses `after` on a truncated board). |
| 13 | Run references | A Kaneo task is `{provider:"kaneo", id}` everywhere: `run_launch` gained `item_provider`, `item_id`, `item_key`; `runs.Links` carries `Item` beside `Issue` (freelancers inherit it). `tracker.RunLinker` stays GitHub-only; a non-`RunLinker` item is resolved with `Tracker.Get` into an `item` run ticket. A Kaneo floor's numeric tickets are never read as GitHub issues. |
| 14 | Prompts | An agent cannot read a Kaneo task (no `gh`, and the key never reaches an agent): the orchestrator's prompt and "Ask a worker…" inline the key, title, URL and description (6000 / 4000 bytes, then a note), and say not to look it up with `gh`. The issue-status line ("move the ticket status…") is replaced, for a Kaneo task, by "leave its status on the Kaneo board to people": the orchestrator has no way to move it. The write-code skill (outside this repo, `~/.agents/skills/write-code/SKILL.md`) still says a referred ticket should be set to Doing/QA; it names no `gh` command, and the prompt's own line overrides it for Kaneo. GitHub's prompts are byte for byte as before. *(Amended 2026-10-17 by #102: the assumption was wrong. That the bridge never passes its key to an agent says nothing about the tools and credentials an agent already has (Kaneo has a CLI and an MCP server that take a task id). A Kaneo task is now named by its canonical URL, which carries the instance, workspace, project and task id (`Kaneo task <key>` when there is none, never a bare number): the orchestrator's prompt is `/write-code <url>` (`$write-code` for Codex) with the team, placement, floor and extra lines and **no** status line, and "Ask a worker…" sends `askPrompt(key, url)` like an issue's and is offered while the description loads or after it failed. GitHub's and free-text prompts are unchanged.)* |
| 15 | "Open in Kaneo" from the helper | The helper's built-in allowlist stays `github.com`. The bridge names its saved instance's web **host** (https, no port) on its own `/healthz` (`X-H3D-Open-Hosts`), which the helper already polls every 5 s through its ssh tunnel; the helper adds it while it is named and drops it when not. Trust: the bridge you ssh to is already trusted (it holds the keys and runs the agents), and no page can set the header (the helper does not proxy `/healthz`). The URL checks are unchanged (https, no credentials, no port). A self-hosted instance on a non-443 port cannot be opened from the helper (the check refuses ports); a later change could add exact origins. Propagation: within one check (≤ 5 s) of a save or a disconnect, no helper restart. |
| 16 | Rate friendliness | Outbound calls run off the hub goroutine, 15 s each, two at a time at most; workspace and project lists are cached 30 s per generation; the floor's project list waits 200 ms after a workspace change and only the newest answer lands (`LatestOnly`), so rapid switching sends few calls and never restores an older project. The lists belong to the connection's generation: a `kaneo.update` with another generation (a new instance or key, a clear, a first connection) drops them and every answer on its way, and an open floor form asks the new connection at once (one opened before Kaneo was connected loads when it is); an answer whose `generation` is not the shown connection's is dropped. The provider's error kinds pass through unchanged; a call that never reached Kaneo is also `kaneoconf.ErrUnreachable`. `Project`, not `ProjectIn`: `VerifyProject` tells gone (`not_found`, a 400 on the id read included) from another workspace's and archived (`bad_request`) itself. |

A board read is bounded per call (15 s, like a test's) and by the provider's 12-call budget; there is no deadline over the whole read, as for GitHub's feed. |

### #184: the Kaneo provider package

The provider half of the entry above, `internal/kaneo`, built against the instance's deployed OpenAPI and the pinned
upstream source (`docs/research/kaneo-api.md`), tested only against `httptest` fakes (no live call). The settings, the
floors, the wire and the wiring in `app` are the table above. Code: `internal/kaneo/`,
`internal/provider/provider.go` (`ErrUnauthorized`, `ErrForbidden`), `internal/tracker/tracker.go` (`Column.Kind`).

| # | Question | Decision |
|---|---|---|
| 1 | What instance URL is accepted | The origin or its `/api` base, with or without a trailing slash; scheme and host lowercased, a default port dropped, `/api` never doubled (`ParseURL` → `Endpoint{APIBase, WebOrigin}`). Refused: anything but http(s), a user or password, a query or fragment (even an empty `?` or `#`), spaces, any other path (a pasted dashboard link is not an instance; sub-path installs are not supported), and plain http off loopback (`localhost`, 127/8, `::1`). |
| 2 | Errors | One kind per status, as the contract pins: 401 `ErrUnauthorized` (its message says the key may be wrong, expired, revoked **or out of quota for now**: Kaneo answers an exhausted key with 401), 403 `ErrForbidden`, 404 `ErrNotFound`, 409 `ErrStale`, 400/422 `ErrBadInput`, 429 `*RateLimitError` (`ResetAt` from `Retry-After`, seconds or a date; zero when absent, which is what Kaneo sends), 3xx (never followed: the key would go along), 5xx, network and timeouts `ErrFailed`; a timeout or cancel also answers `errors.Is(err, context.DeadlineExceeded / Canceled)`. Kaneo's own words (plain text, or JSON `message`) are kept, one line, 160 bytes, with the key and any `Bearer …` replaced by `[key]`; a URL error keeps only its cause. Each call has its own timeout (15 s default) under the caller's ctx; an answer is capped at 16 MiB (a board page can carry 100 descriptions of 64 KiB). |
| 3 | A 400 on a read by id | Kaneo answers an unknown task or project with **400** ("Unknown task, or its workspace could not be determined"), not 404. A read whose only argument is the id (`GET /task/{id}`, `/project/{id}`, `/column/{id}`, `/task/tasks/{id}`, `/comment/{id}`) reads it as `ErrNotFound`; writes keep 400 → `ErrBadInput`. |
| 4 | The connection test | `GET /auth/organization/list` (it is what proves the key; timed for the latency), then `GET /user/me` for the owner's name, optional (its failure is not the test's, a cancel is). Only GETs. An empty list is a success with no workspaces. An entry without an id is skipped; one without a name shows its id. |
| 5 | Projects | `GET /project?workspaceId=` (`&includeArchived=true` only when asked); archived ones and any that names another workspace are dropped on our side too. `ProjectIn(ws, project)` reads `GET /project/{id}` and answers `ErrNotFound` when it is of another workspace (or unknown): what a floor's save checks. |
| 6 | Ids, keys, links | A card's id is Kaneo's task id (opaque); its key `<project slug>-<number>` (the slug alone for a task without a number); its URL `<web origin>/dashboard/workspace/<ws>/project/<project>/task/<task>` (by ids: no rename breaks it). The fetch identity is `Tracker.Key()` = `kaneo:<API base>\|<workspace>\|<project>`, never the key; the app appends the connection's generation (`\|g<n>`, row 18 above). |
| 7 | Columns | **Planned first, the workflow columns in position order, Archived last, the two virtual ones always present** (also empty), with `Kind` `planned`/`archived`: a card can be moved into an empty bucket, and the column set does not change with the cards. Archived is not completion: only a column with `isFinal` is `Done`, and a card is `closed` only there. A workflow column whose slug is `planned` or `archived` replaces the virtual one; a task whose status only the board pages name (a column made since the column list was read) gets that column, before Archived. Column ids are slugs (what a task's status holds), never the column list's database ids. |
| 8 | How much a board read does | `limit=100`; task pages followed through `totalPages` up to **5** (500 tasks), each task page's related pages (labels, links, columns) through `relatedTotalPages` up to **3**, and at most **12 calls** a read, the column list included. Past any of them, when `pagination.total` changes during the read, or when the read ends with a number of distinct tasks other than `pagination.total` (the board moved under it: a reorder between pages repeats one task and skips another with the total unchanged), the board is `Truncated`; the next poll reads it whole. Labels are merged by id across related pages (Kaneo repeats the page's tasks on each), a task is a card once. A small project is 2 calls a poll; the worst is 12, so a watched Kaneo floor (60 s) spends at most 12 of the key's default 100 calls a minute. No rate headers exist: `Board.Rate` is nil. Final-column tasks are all read (no seven-day window: Kaneo gives no completion time). |
| 9 | Card fields Kaneo lacks | `UpdatedAt` 0 and `ClosedAt` nil always (the schema has neither; `createdAt` is not relabeled), `Author` "" (a task's `userId` is its assignee; no creator is exposed), so `Detail.Author` is empty too. `Position` is the card's rank in its column in Kaneo's order (position, then id; none last); the raw positions stay inside for the reorder. Priority `urgent/high/medium/low`, `no-priority` and anything else none; label colours `#rrggbb` (`#abc` widened, anything else grey); the one assignee with its avatar. |
| 10 | Get | `GET /task/{id}?view=detail`, then the check that it is of this project (and workspace, when the detail says) else `ErrNotFound`, before anything else is read. A deferred description (`descriptionDeferred`) is read through `GET /task/{id}/description` page by page carrying the version; a change under the read (409) starts it over once, a second is `ErrStale`; past 64 pages it is an error, never a silently cut body. The card is the last board's (labels, avatar, rank; a board is read when there is none yet) with the detail's title, status, priority and assignee (the rank dropped when the column changed); a task off the board is made from the detail alone. Comments: `GET /comment/{id}`, all of them (Kaneo has no paging), so `CommentsTruncated` is false. |
| 11 | Comment | A blank body or one over **10,000 UTF-16 code units** (what Kaneo's validator counts: a 4-byte rune is 2) is `ErrBadInput` before any call. The task's scope is checked with a fresh detail read, then `POST /comment/{id}` `{content}`. The answer is an activity row without an author, so the comment list is read again for it; when that read fails the comment is still returned (it landed), without its author. |
| 12 | SetStatus | The column must be a column of the last board (one is read when there is none). Without an anchor: the scope from a fresh detail read, then `PUT /task/status/{id}` `{status: slug}`. With one: **one** `POST /task/reorder`: the destination column numbered 0..n-1 in its new order, only the cards whose position changes sent plus the moved one with its status, and `expectedTasks` every task of the column it leaves and the one it enters as the last board has them (raw positions, null kept), so Kaneo answers 409 (`ErrStale`) when the board changed since; Kaneo itself refuses a task of another project (404). A moved card or an anchor that is not where the last board says is `ErrStale` without a call; a truncated board cannot be ordered (`ErrUnsupported`: Kaneo would refuse every snapshot). The answer of either write updates the last board, so a second drag in a row is computed from Kaneo's state. |
| 13 | Close, DELETE | `Close` is `ErrUnsupported` (`Info.Capabilities.Close` false): completion is a move to a final column. No code path sends a DELETE (`TestNoDelete`; the fake fails any test that would). |
| 14 | Concurrency | Board reads are one at a time; the last board is behind a mutex, and the writes and Get read and update it under it. Two moves computed from the same board both go: the second is refused as stale by Kaneo. |
| 15 | Boundaries | `internal/kaneo` imports the standard library, `provider` and `tracker` only (`TestKaneoIsAProviderLeaf`); only `app` imports it (`TestBoardLayerIsProviderNeutral` checks both that `server`, `store` and `proto` do not and that `app` does). |
| 16 | Unreachable | A round trip that failed (DNS, refused, TLS) is `provider.ErrFailed` with `ErrUnreachable` and the network error as its cause, so the settings tell "could not be reached" from "Kaneo failed"; its message is unchanged and never the cause's. |

In a transcript, `@r:` (or `@repo:`) lists the repositories and folders configured on the other floors of the worker's

| # | Question | Decision |

## 2026-10-15 — #54: Repository discovery

`@r:` listed only what other floors were configured with. Now the bridge also scans folders on its host for Git
checkouts and merges them in, without duplicates. Code: `internal/repodisc` (walk, git lookups, identity, the
service), `internal/server/repodiscovery.go` and `repos.go` (`mergeRepos`), `internal/store/repodiscovery.go`,
`game/src/world/repoDiscovery.ts`, `game/src/laptop/repoSearch.ts`, `game/src/ui/repoDiscoverySection.ts`.
Research and measurements: `docs/research/repository-discovery-architecture.md`,
`docs/research/repository-scan-bench/README.md`.

| # | Question | Decision |
|---|---|---|
| 1 | Traversal | **Stop at each checkout boundary**: `Lstat <dir>/.git` (folder, file or link) before listing a folder; a marker makes it a candidate and the walk does not enter it. Every other folder is walked, at any depth, whatever its name: no depth cap and no dependency-name exclusions (the boundary already skips `node_modules` inside checkouts, which is where the cost was: `find -prune` took 8.7 s / >30 s on the two roots, the boundary walk 35 ms). Symlinked subfolders are not followed; explicit roots are resolved (`EvalSymlinks`), so an alias root is walked once. A repository nested in a checkout is found only from its own root, which is always walked even inside another root's checkout. Bare repositories are out of scope. The Settings section's "What is scanned" says so. |
| 2 | Git | Only for candidates, through two new allowlisted `gitops` shapes (`rev-parse --path-format=absolute --show-toplevel --git-common-dir`, `remote get-url origin`), 8 at once, 2 s each, no network. Every `gitops` command now also drops inherited `GIT_DIR`, `GIT_WORK_TREE` and the other repository-locating variables: a bridge started from a hook would otherwise point every `-C` call at one repository. Not `gitremote.Resolver`: it knows only GitHub, and discovery must list local-only and non-GitHub repositories. |
| 3 | Identity | A repository is the checkouts sharing a canonical Git common directory (worktrees) or a GitHub origin normalized by `gitremote.ParseGitHub` (ssh / https, case, `.git`). Nothing else merges: same-name folders, or two clones of one non-GitHub remote, stay apart (identity cannot be established safely). Its id is `gh:<owner/repo>` lowercased, else `git:<common dir>`. Checkouts in order: main checkouts (common dir is their own `.git`) first, then by path. |
| 4 | Merge with floors | Server-side, for **both** `worker.repos` and `hire.repos`, off the hub goroutine. A floor's identity is its `repo`; a folder-only floor's, the discovered repository of the checkout its folder is in (an `Lstat` walk up, symlinks resolved: subfolders and aliases match without a git call), else that checkout's origin, else the checkout, else the folder. One row per identity at the first floor's place. Winner: the first floor (floor order) with a usable folder, else the discovered checkout (main, then path), else the GitHub URL. The row keeps that floor as provenance and always carries the path it puts in (shown). Discovered-only repositories follow, by name. The all-buildings switch still governs only floor sources. |
| 5 | Row shape | `RepoRef` gains `id` (stable, opaque: the popup key) and `source` (`floor` / `discovered`), and `checkouts`; `session` is absent on a discovered row and `building` null. **No fake floor.** An older browser drops discovered rows (they have no `session`) and keeps floor rows; the new browser keys an older bridge's rows `floor:<session>`. |
| 6 | Service | Bridge-owned, wired by `app` with the bridge context (the `fileindex` precedent). `Configure` and `Refresh` never block (the hub calls them on its goroutine): a change of roots bumps a generation, cancels the scan in flight, drops removed roots' entries at once and asks for a scan; a result whose generation is old is thrown away, so a removed root never comes back. One scan at a time, bounded to a minute. Readers get an immutable `Catalog`; its `revision` moves only when its content does, so `repo_discovery.update`s for progress (at most every 250 ms) do not make a popup ask again. |
| 7 | Failures | Per root: a root that cannot be resolved or read, that runs past the bound, or where git answered for no candidate fails and **keeps its last successful result** (`stale`, with the error), never touching the other roots; never scanned successfully is `error`. A candidate git could not answer for (a timeout) keeps its previous entry; a failed origin lookup keeps the previous origin. Unreadable subfolders are skipped with a warning. |
| 8 | Settings | Their own table and messages (`repo_discovery_settings`, `repo_discovery.*`), not `repo_refs`: a separate section with its own validation and status, and `repo_refs` stays a one-field switch. Validation is syntactic (absolute, no line break, ≤ 4096 bytes, once after cleaning, ≤ 32 roots; 1–1440 minutes, default 10), checked by the browser first and again by the bridge (`bad_request` in words); existence is a scan result, so a temporarily unmounted root can be set. Without roots discovery is off. |
| 9 | Performance target | Warm full scan (walk + git validation + origin + identity merge) **under one second** on the two supplied roots; measured 151.5–168.9 ms median, p95 ≤ 176 ms, over four runs of 20 scans (`TestBenchRoots`, `docs/research/repository-scan-bench/production-results.jsonl`). No watcher: a 10-minute schedule plus Refresh now. |

## 2026-10-16 — #81: "Open in GitHub" on a Linux helper

`POST /api/open` answered 502 `opening a browser needs macOS` on every OS but darwin. Now `SystemOpen`
(`internal/helper/open.go`) runs `open <url>` on macOS and `xdg-open <url>` on Linux, and names the OS elsewhere.

| # | Question | Decision |
|---|---|---|
| 1 | Is a command that is still running a failure? | **No.** `xdg-open` stays in the foreground as long as the `.desktop` app it started lives (browser not running). The opener waits a 3 s grace window: exit 0 → opened; non-zero exit or no such executable → error with the exit code and the first 512 bytes of output (`502`); still running → opened, **not killed**, reaped by a background goroutine (no zombie), its late exit unseen. The old 15 s `CommandContext(...).CombinedOutput()` would have killed a good launch and reported it failed. |
| 2 | Pipes | stdin none. stdout and stderr are **one pipe the helper owns** (`os.Pipe`, the write end handed to the command as an `*os.File`, so Go starts no copy goroutines and `cmd.Wait` returns at the command's exit, never later because a descendant holds the pipe; `Cmd.WaitDelay` is not used). The helper closes its write end right after `Start`; one reader goroutine keeps the first 4 KiB, discards the rest until EOF (every writer gone) and then closes the read end, never earlier, so a browser the opener started that logs to the inherited stdout/stderr later never gets EPIPE/SIGPIPE. After a non-zero exit the answer waits at most 150 ms for that reader to reach EOF (so output already written is in the diagnostics), no longer, so a descendant cannot delay it. Round 1 used `WaitDelay` and `ErrWaitDelay`: a late non-zero exit near the end of the window, with a descendant on the pipe, came back after the timer and was reported as success (reviewer repro `sleep 4 & sleep 2.75; echo failure >&2; exit 4`), and the pipe was closed under later writers. A timer that fires at the same moment as an exit still reports the exit. |
| 3 | The request's context | Ending (the game went away) ends the wait with that error and **leaves a launch in flight alone**: killing it would only make a half-opened browser. A context already done starts nothing. |
| 4 | macOS | Shares the runner: `open` returns at once, so success is `204` and failure `502` with diagnostics, as before; only the 15 s kill is gone. |
| 5 | Environment | Inherited whole (`Cmd.Env` unset); no display, runtime dir or browser path is set. The user-service requirements are in CONTRIBUTING.md, "Linux user service". |
| 6 | Tests | `newSystemOpener(goos, command, grace)` takes the OS, the command constructor and the window, so every OS is driven on any host; most tests run real fake `xdg-open` scripts on `PATH`, never a browser. |
