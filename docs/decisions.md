## 2026-09-30 — #51 (and #13): images reach the agents through Drop Zone, over HTTP

| # | Question | Decision |
|---|---|---|
| 1 | The transport of an image: the `/ws` chunks #13 specified, or HTTP? | **HTTP: `POST /upload` with the raw bytes**, through the helper to the bridge, beside the logos (M3d). The WebSocket reads whole messages up to 256 KiB (`maxClientMsg`; fragmenting one message does not get round that cap), so an image of up to 25 MiB would need base64 or binary chunks with an offset protocol, a per-connection transfer state, acks, cancellation and audit redaction. HTTP gives the streaming, the status codes, the body cap and the cancellation (a closed request) for free, does not queue behind or block the control traffic of the one socket, and the logo routes are the precedent for the topology (URL derived from the WebSocket URL, token kept, Host/Origin guards, the token and `Origin` not forwarded). It changes #13's stated transport; the rest of #13 (Drop Zone, one file per request, 25 MB, markers) stands. |
| 2 | Drop Zone's contract | Facts read from its source (`internal/upload/handler.go`, `store.go`): `POST /upload` multipart with the `file` part; an optional `name` field **only counts if it comes before the file part**; one file is stored under its sanitised stem and original extension, **two or more file parts become a `tar.zst`** (so one request per image); the file is spooled and claimed into a date folder **only after the whole body parsed**, with `-2`, `-3` for a collision (so the path is never predicted); success is `200 text/plain` with the absolute path and **one** line feed. It has no authentication, size cap or type check: the bridge owns those. The client never supplies the upstream URL (`--dropzone-url`, default `http://127.0.0.1:8080`) and the bridge never writes the drop directory itself. |
| 3 | Size | **25 MiB** (`25 << 20` = 26214400 bytes), counted on the bytes read (`http.MaxBytesReader` in the bridge, plus one byte past the cap as a sentinel in the streaming), never on `Content-Length`. A screenshot is a few MB; a retina PNG with a lot of detail can pass 10. MiB not MB, so the number is a power of two the game can show and compare exactly. Over the cap is `413`, and the request to Drop Zone is **aborted without the multipart footer**: a plain `LimitReader` would cut the image short and still finish the body, storing a truncated file. The helper allows the cap plus 4 KiB (also for chunked bodies) and leaves the exact verdict to the bridge. |
| 4 | Type checking | **Sniff, do not decode.** The first 512 bytes go through `http.DetectContentType`; only PNG, JPEG, GIF and WebP pass, the extension follows the sniff (`.jpg` for JPEG), the part carries the sniffed type, and the client's `Content-Type` and file name are hints nobody looks at (an SVG or HTML labelled `image/png` is `415`). Decoding would cost memory for a 25 MiB screenshot and prove little; the agents' own readers say if a file is corrupt. |
| 5 | Name | `h3d-<label>-<n>`: the label a hint from the client, cut down to `[a-z0-9-]` and 24 characters (`hire` when empty), `n` the image's sequence in the draft. Not the client's file name. The number in the stored name need not match the `[Image #n]` marker (that is document order); no file is renamed after a reorder. |
| 6 | Lost answer | **An orphan is accepted.** If the connection drops after Drop Zone stored the file, nobody references it and a retry stores another (`-2`). The bridge cannot delete it (Drop Zone has no delete, and the bridge does not write its directory) and should not guess what is its own. |
| 7 | Concurrency and time | At most 4 uploads at once (a fifth is `429` `upload_busy`, not queued: a queue would hold a client's body open), 2 minutes for the whole upload (`504` `upload_timeout`), 5 s to connect, 30 s for Drop Zone's answer after the last byte, no redirects (an image is never replayed elsewhere). The pipe to Drop Zone is closed when the context ends: the HTTP transport waits for its writer, which waits on the pipe, so cancelling a context alone would hang. |
| 8 | Audit | Rows `image.upload` with label, `n`, size, type and outcome; never the bytes, and not the path (an audit row is not where a path is needed). |

## 2026-09-30 — #51 (M11 #13): the shared prompt composer

Built as a standalone module (`game/src/ui/composer/`, `game/src/net/upload.ts`); the hire dialog, the P overlay and the start-run instructions are wired to it in a later round.

| # | Question | Decision |
|---|---|---|
| 1 | `contenteditable` with chips, or a textarea with a thumbnail strip? | **`contenteditable` with atomic chips.** #51 asks for the image inline, at the caret, in order with the text; a strip cannot say where in the text a picture was. One component for every prompt, not a hire-only fork. The editor is vanilla (no editor library): plain text and chips only, so the browser edits text natively and everything it cannot be trusted with goes through our model (chips, paste, drop, Enter, delete beside a chip, undo). If IME or history acceptance fails on the Mac browsers, the fallback is a framework-neutral editor core behind the same `Composer` API, not scattered browser hacks. |
| 2 | Model shape | **One string plus the occurrences.** The document is a string in which each image is one U+FFFC, and the list of image occurrences in that order. A caret or a selection is an offset; ranges are `slice`s; "between two chips" and "two chips side by side" need no cases. Text is cleaned at the boundary (CRLF/CR → LF, U+FFFC and U+200B dropped). An occurrence (one chip) points at a **resource** (the bytes and their upload): the two ids differ so one upload can serve two chips and every chip stays editable. The marker number is never stored: it is the occurrence's place in the document. The DOM is drawn from the model and read back on `input`; chips are `contenteditable=false` wrappers with separate preview, retry and remove buttons; an empty text run is a U+200B text node so a caret has a place beside a chip. |
| 3 | Serialiser | `[Image #n: <path>]` in **document order**, path exactly as Drop Zone returned it (absolute, no `]`, no control characters or line breaks, else an error and nothing is sent), text verbatim, brackets the user typed are never read. No trailing hint by default (an option adds one line; no experiment has said it is needed). Cap in UTF-8 bytes, checked on the final text: hire 32 KiB, `worker.prompt` 16 KiB, passed in by the host. `resolve()` never returns partial text. |
| 4 | Uploads | Per image, as soon as it is pasted (eager), at most 2 at a time, `pending → uploading → ready(path) \| error`, one `AbortController` and an `attempt` per resource so an answer for a removed or retried image is ignored. A removed chip cancels its upload; undoing the removal queues it again. `resolve()` waits for the images the document uses, and is `ok:false` with the failed images (never a partial prompt) if any failed; it does **not** retry a failed image by itself (a broken Drop Zone is not hit by every Enter): the chip's Retry does, and a ready image is never sent twice. HTTP `POST /upload` per the shared contract (`net/upload.ts`, like the logos). |
| 5 | Limits | 20 images per prompt (our opinion, not the ticket's), `UPLOAD_MAX_BYTES` = 25 MiB each, PNG/JPEG/GIF/WebP by type or (no type) extension, empty files refused, each with a friendly message; the bridge stays the authority (sniffed bytes). Object URLs are kept while the draft, its history or an open preview can show the image, then revoked. |
| 6 | Undo | **One history** in the draft for text and images (100 steps; typing within 1 s is one step); the browser's own undo is never used (`beforeinput` history types and Ctrl/⌘+Z, Shift+Z, Y are ours). Covered: typing, IME commit, text paste, chip insert/remove, selection replacement. Not covered: upload progress and preview open/close are not history. |
| 7 | Enlarged view | A second native modal `<dialog>` (top layer, so it shows over a modal host; inert below). **Esc closes only it**: a capture-phase keydown on `window` closes it and swallows the key, and `cancel` of the preview and of the host (capture, before the host's own handler) are refused while it is open (the research probe found two nested dialogs can both close on one Esc). | 9 | Deliberately out | Recent drops, office-context markers and non-image `[File: …]` chips (#13's later parts); IndexedDB / localStorage persistence of pending images across a reload (a text-only save is left to the host); dragging chips to reorder (`moveImage` exists in the model, no gesture yet); zoom/pan and next/previous in the enlarged view; a drop-position indicator (the editor is highlighted); dedupe of identical images (two pastes are two chips); re-encoding or downscaling (bytes go up as pasted); HEIC/TIFF. ## 2026-09-30 — #56 (M16 phase 2): images in the transcript view, the Images tab and the desk prints

| # | Question | Decision |
|---|---|---|
| 1 | Where the bytes live | **Not in items.** An item carries an `ImageRef` (sha256 of the bytes, sniffed mime, size, `origin` input/agent, `kind` generated/viewed, the item it is in). Bytes are served by `transcript.image` for a hash **this connection was sent**, so a client cannot ask for what it was not shown and never names a path. Inline images are decoded and hashed once per transcript line (remembered by line offset), filed in a 64 MiB LRU (`imgcache`) plus an optional 0600/0700 disk cache, and read again from their line when neither has them: the cache can be small and lose things. |
| 2 | Path images | Only under an allowlist: Drop Zone's data, `~/.codex/generated_images`, the worker's cwd and the exact file of a Codex `view_image`. The check is lexical first (a path outside every root is refused **before any file system call**, so an outside file is not even looked at), then again after `EvalSymlinks`, then regular file, image bytes, <= 25 MB. The read itself does not reuse the checked path: it walks down from `/` along the real path one component at a time with `O_NOFOLLOW` (`O_PATH` for the directories on Linux, so a pass-through-only directory still works; any directory swapped for a link after the check, below the root, the root itself or one above it, is refused), opens the file non-blocking (a FIFO swapped in cannot hold the bridge) and checks the opened descriptor. The cost is that a path reached through some other symlink than the root's own spelling is refused; that is the safe side. |
| 3 | Thumbnails | Cut on demand (pure Go, CatmullRom, at most 2 at once), cached with the images; JPEG stays JPEG, the rest is PNG. Full images are capped at 12 MiB of base64 (`too_large`; the view says so and keeps the thumbnail). |
| 4 | Images tab data | `transcript.images` lists the whole session from the offset index (an item flagged as having images is read back once); it is not the watch's 200-item window. ## 2026-10-09 — #215: a report request can be resolved without resuming the worker, and is kept whole

A coder that ended its turn with `input_required` in its report stayed NEEDS YOU / "Waiting for an answer" after the orchestrator accepted the request in its ledger and moved on: nothing in the report changed. The request was also cut to 500 bytes, losing the decision itself.

| # | Question | Decision |
|---|---|---|
| 1 | The resolution signal | A **sidecar file**, `<run>/<stem>.resolved.json` next to `<run>/<stem>.json` (`runs.ResolvedName`), `{"report", "resolved_by"?, "note"?}`, written atomically by the orchestrator. File-based like the report itself: it survives a bridge restart with no store (`TestReportRequestResolution` starts a second bridge over the same directory). No command or protocol call: the orchestrator already writes files in this directory and the bridge never writes there. |
| 2 | Binding | The sidecar resolves the report only if its **mtime ≥ the report's**, compared at read time. A report rewritten later (a new request) asks again; a fresh report path starts over as before. The sidecar is **bound to its report** (round 2): it must carry a string `"report"` equal to the report's file name, so derived names that collide (`coder-r1` / `coder-r1.json`) and another worker's report JSON dropped there resolve nothing. Names ending `.resolved.json` are **reserved**: `runs.ValidReport` makes one an invalid report (`Initial`, `reportWorkers`), so a worker never occupies a sidecar path. A name whose sidecar would exceed 80 bytes has none. |
| 3 | Safety | The same reads as the report: `Lstat`, `O_NOFOLLOW`, `O_NONBLOCK`, regular files only, 4 KiB cap; garbage, a non-object, non-string fields (`null` included), a missing or different `report`, a symlink, a FIFO or an oversize file is **ignored** (the request stays active: a broken resolution must never silence a real request). Note cut to 300 bytes, `resolved_by` to 40, UTF-8 safe. |
| 4 | Tracking | The poller (`reportTracker`, off the hub goroutine) stats the report **and** its sidecar and re-reads when either stamp changed, so creating, replacing or deleting the sidecar is one `worker.upsert` within the poll interval. |
| 5 | Wire | `report.input_resolved {by, note?, at}`; `input_required` stays present (the card shows the note, the text is history). Also `input_truncated` and `input_for`. |
| 6 | An unresolved request is never suppressed by `done` | The agent being `done` says nothing about whether its report's request was settled; the report is the only source. Resolved, the request contributes nothing: `crew.ts` `inputRequired` is null, so lifecycle falls back to the real status, `needsYou` is false, and every consumer (counts, N, inbox, badges, bubbles, delivery) follows because they all read `display`. The delivery walk treats a resolved request like an answered one (the folder is handed in). |
| 7 | The whole request | `MaxInputRequired` 8 KiB (reports are ≤ 256 KiB), UTF-8 safe, flagged `input_truncated`. | 8 | Wording and who decides | "Report request", never "Waiting for an answer" (the agent asked no question); "Asked of the orchestrator (Cog)" / "Asked of you": the report's optional `input_for`, else the orchestrator when the worker has one (`orch_id`), else you.
