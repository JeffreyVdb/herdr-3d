# Verification: engine / rendering stack

Date: 2026-09-28. Original: [engine.md](engine.md). **Verdict: CORRECTIONS.**

## TL;DR

The three.js + TypeScript recommendation remains sensible for an agent-driven game, and the Linux SwiftShader and Mac Metal probes support its feasibility. The proposed **Mac URL is wrong for WebGPU**: `http://devbox:5173` is a remote, insecure origin, so `navigator.gpu` is unavailable and three.js falls back to WebGL2. The successful Mac probe used `http://localhost`, which has a secure-context exception. Serve the app over HTTPS (for example, Tailscale Serve) or SSH-forward the server port to the Mac and browse `http://localhost:5173`. Vite also rejects a custom HTTP hostname unless it is placed in `server.allowedHosts`. The claim that three.js is the only candidate with a server-to-Mac browser loop is too strong: Babylon.js has the same browser and WebGPU/WebGL paths. The suggested `mac-shot.sh` example fails to pass its fixture argument to the remote command. Performance for the actual city and terminal UI remains unmeasured. These corrections affect the workflow, not the basic engine choice.

## Omissions and impact on the recommendation

1. **Secure origin is a launch requirement.** The smallest change to the workflow is to expose the Vite+bridge app as `https://...example.net` via Tailscale Serve; its HTTPS feature must be enabled in the tailnet. A local SSH port forward and `http://localhost:5173` also preserves HMR and WebGPU. For either route, proxy the bridge under the same origin and verify `wss:` when the page is HTTPS. [WebGPU secure-context rule](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API); [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve).
2. **The three.js choice remains a preference, not a unique capability.** Babylon.js deserves a small matching prototype if built-in GUI/animation/scene tooling matters. raylib 6.0's new software framebuffer should be mentioned in its test-loop score. [Babylon WebGPU support](https://doc.babylonjs.com/setup/support/webGPU); [raylib 6.0](https://github.com/raysan5/raylib/releases/tag/6.0).
3. **Validate the scene that matters.** Benchmark the expected number of buildings/floors/workers, desk screens, transparent cutaways, shadows and GLBs on the Mac in a headed browser. The current three-tower images only prove that a simple scene renders. Use a separate readability test for terminal text at desk zoom; DOM/CSS overlays need screen-space tracking, occlusion and interaction rules.
4. **Separate observed results from causes.** `screencapture` failure is reproducible, but the claimed specific Screen Recording permission cause was not proven. Godot + Xwayland rendering and Tauri remain untested. None blocks starting with the corrected browser workflow.

No existing herdr session, workspace, or pane was changed. The original `engine.md` was not edited.
