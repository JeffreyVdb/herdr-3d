# Local prompt secret detection: candidate and source review

Investigated 2026-10-18. Scope: detect exact credential spans in a user's prompt locally, replace them with references to session-scoped files, and prevent credential values reaching model-visible prompts or output. This note records source findings; measured results belong in the companion benchmark report. Searches used Alterlab MCP; primary model cards, repository documentation and source code were read directly.

## Recommendation

Benchmark a hybrid: Gitleaks for known credential formats and a credential-aware GLiNER model for contextual passwords and unfamiliar tokens. Start with Knowledgator GLiNER PII edge/small for CPU cost, and compare Fastino GLiNER2 PII if resources allow. None of the reviewed published PII scores establish recall for developer credentials in conversational prompts; selection requires an exact-span credential benchmark, clean negative prompts, and per-type results. This is an inference from the candidate capabilities and evaluation domains below.

| Candidate | Local deployment and commercial use | Relevance to this task | Priority |
| --- | --- | --- | --- |

| `knowledgator/gliner-pii-edge-v1.0` | Apache-2.0; PyTorch and published ONNX | Smallest reviewed credential-aware contextual option; card explicitly includes password and runtime custom labels | First CPU candidate |

## GLiNER: practical differences and caveats

GLiNER is a span-producing encoder: labels are supplied at inference, so it can attempt unseen categories without generative output. The framework documents CPU inference, ONNX export and quantization. Credential extraction should request credential labels only; broad PII labels would also remove names, emails, addresses and other data outside the requested feature. [GLiNER repository](https://github.com/urchade/GLiNER)

The Knowledgator PII cards explicitly list `password`; they allow custom labels. Suggested exploratory labels are `password`, `api key`, `access token`, `secret key`, `private key`, and `connection string`, with threshold sweeps rather than assuming defaults. Coverage of all those credential categories is a benchmark question, not a capability demonstrated by the model card. The cards report aggregate synthetic PII precision/recall/F1: edge 78.96/72.34/75.50%, small 78.99/74.80/76.84%, base 79.28/82.78/80.99%. These are publisher results on their PII dataset, not our measurements or credential recall. The cards contain copied examples (the small card's quick start loads base) and an inconsistent sentence claiming base has the best F1 while the table lists a higher large-model F1; use the actual model ID and artifacts. [Edge card](https://huggingface.co/knowledgator/gliner-pii-edge-v1.0), [small card](https://huggingface.co/knowledgator/gliner-pii-small-v1.0), [base card](https://huggingface.co/knowledgator/gliner-pii-base-v1.0)

Artifact sizes were checked against each model's Hugging Face file-tree API, rather than assuming the card's generic size table applies to every variant:

[Edge files](https://huggingface.co/knowledgator/gliner-pii-edge-v1.0/tree/main), [edge ONNX](https://huggingface.co/knowledgator/gliner-pii-edge-v1.0/tree/main/onnx), [small files](https://huggingface.co/knowledgator/gliner-pii-small-v1.0/tree/main), [small ONNX](https://huggingface.co/knowledgator/gliner-pii-small-v1.0/tree/main/onnx), [base files](https://huggingface.co/knowledgator/gliner-pii-base-v1.0/tree/main), [base ONNX](https://huggingface.co/knowledgator/gliner-pii-base-v1.0/tree/main/onnx)

The current edge/small configurations use a ModernBERT backbone and token-level mode, while base uses DeBERTa and markerV0. All three configs specify a whitespace word splitter, `max_len=2048` and `max_width=12`. Despite the name, GLiNER's `WhitespaceTokenSplitter` uses `\w+(?:[-_]\w+)*|\S`: standalone punctuation is a separate word token. For example, a password ending in `!` requires the model to include that punctuation token in the detected span; the splitter does not discard it. This makes tokenizer boundaries, punctuation next to credentials, long inputs and multiline key blocks mandatory extraction tests. Treat config fields as model parameters, not a guarantee that every 2,048-character or 2,048-word prompt fits; subword tokens and label overhead matter. [Edge config](https://huggingface.co/knowledgator/gliner-pii-edge-v1.0/blob/main/gliner_config.json), [small config](https://huggingface.co/knowledgator/gliner-pii-small-v1.0/blob/main/gliner_config.json), [base config](https://huggingface.co/knowledgator/gliner-pii-base-v1.0/blob/main/gliner_config.json), [splitter implementation](https://github.com/urchade/GLiNER/blob/main/gliner/data_processing/tokenizer.py)

Fastino's PII model is particularly relevant because it advertises the five credential labels above. It supports English, French, Spanish, German, Italian, Portuguese and Dutch; the card states 4,910 fully synthetic training texts and 42 labels. Its published SPY evaluation is legal/medical PII: average exact-span F1 .477, not a developer-secret benchmark. That comparison cannot establish production credential recall. Its config has `max_width=8`. [Model card](https://huggingface.co/fastino/gliner2-privacy-filter-PII-multi), [config](https://huggingface.co/fastino/gliner2-privacy-filter-PII-multi/blob/main/config.json)

Use GLiNER2's `include_spans=True` and `include_confidence=True`. The official repository documents original-text exclusive-end character offsets and overlapping-chunk long-document extraction. Its default whitespace splitter matches public training; changing splitters can alter quality. The PII card's redaction example calls a different model ID and searches strings using `text.find`; do not copy it into security-sensitive replacement logic. Use returned spans and verify `text[start:end]` against the expected value, including repeated credentials. [GLiNER2 extraction and splitters](https://github.com/fastino-ai/GLiNER2), [PII card example](https://huggingface.co/fastino/gliner2-privacy-filter-PII-multi)

The current GLiNER2 repository also documents GLiNER2.5 boundary models, including a 74M small model, with arbitrary span length within an encoded window. Those are general extraction models; do not assume they outperform credential fine-tunes. Boundary models require `AutoExtractor`, while legacy `GLiNER2` loads span models. Current installation distinguishes the local inference extras (`gliner2[local]`) from the lightweight hosted API client; select the local path. An ONNX deployment claim for GLiNER does not automatically establish support for GLiNER2's different runtime. [GLiNER2 repository](https://github.com/fastino-ai/GLiNER2)

Other PII options: `urchade/gliner_multi_pii-v1` is Apache-2.0 and multilingual, but its advertised training labels emphasize personal/financial IDs rather than API credentials. NVIDIA's `gliner-PII` is 570M, returns `{text,label,start,end,score}`, supports CPU, and permits commercial/noncommercial use under the NVIDIA Open Model License rather than Apache/MIT. These are viable comparison candidates, with weaker CPU/credential fit than the shortlist. Gretel's `gretel-gliner-bi-small-v1.0` card is Apache-2.0 and PII/PHI-focused; verify each specific model's license instead of generalizing across GLiNER variants. [Urchade card](https://huggingface.co/urchade/gliner_multi_pii-v1), [NVIDIA card](https://huggingface.co/nvidia/gliner-PII), [NVIDIA model license](https://www.nvidia.com/en-us/agreements/enterprise-software/nvidia-open-model-license/), [Gretel small card](https://huggingface.co/gretelai/gretel-gliner-bi-small-v1.0)

## Heuristic and integration alternatives

Gitleaks scans stdin directly and exposes regex, keyword prefilters, entropy thresholds and `secretGroup` capture selection. It fits an existing Go bridge without a persistent ML runtime. Findings include `Secret`, `Match`, line and column fields. Those coordinates describe the regex match; a rule's captured secret may cover only a substring, so a production adapter must recover the exact captured span rather than blindly replacing the whole location. Its Go regex indices are byte-based, requiring deliberate conversion when composing with Python character offsets or JavaScript UTF-16 indices. Existing allowlist/ignore behaviors need deliberate policy for user prompts so pasted scanner-ignore comments cannot bypass detection unintentionally. [Gitleaks documentation](https://github.com/gitleaks/gitleaks), [Finding structure](https://github.com/gitleaks/gitleaks/blob/master/report/finding.go), [matching implementation](https://github.com/gitleaks/gitleaks/blob/master/detect/detect.go)

detect-secrets offers `detect_secrets.core.scan.scan_line` for ad hoc strings. `PotentialSecret` retains a `secret_value` in memory, while serialized baseline records hash values; neither is a direct exact-span replacement API. A detector adapter must locate every occurrence or capture spans at regex time, including identical values appearing multiple times. Code-oriented keyword and entropy detectors may miss ordinary-language low-entropy passwords; this needs measured per-category recall. Credential verification exists in its filter system, so keep benchmarks and production prompt detection offline and avoid optional verification filters. [String scanning source](https://github.com/Yelp/detect-secrets/blob/master/detect_secrets/core/scan.py), [PotentialSecret source](https://github.com/Yelp/detect-secrets/blob/master/detect_secrets/core/potential_secret.py), [verification filter](https://github.com/Yelp/detect-secrets/blob/master/detect_secrets/filters/common.py), [detector documentation](https://github.com/Yelp/detect-secrets)

Presidio provides regex/context/custom-recognizer composition and a GLiNER recognizer. Its GLiNER adapter directly maps model `start` and `end` into Presidio results and supports an ONNX load option. Its default supported entities emphasize PII rather than a comprehensive API-secret catalog. It could compose the same detectors, but adds integration/runtime work to a Go bridge and does not itself solve unknown credential recall. [Supported entities](https://github.com/microsoft/presidio/blob/main/docs/supported_entities.md), [GLiNER recognizer](https://github.com/microsoft/presidio/blob/main/presidio-analyzer/presidio_analyzer/predefined_recognizers/ner/gliner_recognizer.py), [result offsets](https://github.com/microsoft/presidio/blob/main/presidio-analyzer/presidio_analyzer/recognizer_result.py)

TruffleHog advertises 800+ credential types and active API verification. For this feature, verification must be disabled (`--no-verification`) and unverified findings must be retained; filtering to verified values would silently discard synthetic, expired and untested secrets. Its raw JSON includes secret material, so normal CLI logging/reporting is unsuitable for real prompt values without strict confinement. AGPL-3.0 distribution obligations and subprocess/runtime cost warrant a separate fit decision. [Official documentation and CLI flags](https://github.com/trufflesecurity/trufflehog), [license](https://github.com/trufflesecurity/trufflehog/blob/main/LICENSE)

## Benchmark and product criteria inferred from the review

- Use generated inert secrets only; never validate against providers. Include provider-shaped keys, arbitrary tokens, low-entropy passwords, PEM/SSH blocks, JWTs, authorization headers, credential URLs, JSON, shell assignments, punctuation, Unicode, repeats and multiple secrets in one prompt.
- Report exact-span precision/recall and full-secret containment separately. An overlapping prediction that leaves a token suffix exposed is not a successful redaction. A prediction including neighboring punctuation may redact safely but corrupt the file value.
- Report no-secret false positives, per-type misses, cold start, warmed p50/p95, short/long prompts, peak RSS, model download bytes, pinned model revision and package versions. Tune thresholds on separate examples rather than the reported evaluation set.
- Test union/hybrid detection explicitly. A contextual model can supplement a format scanner, but combining predictions also combines false positives and span conflicts.
- A file path only protects the initial prompt. If an agent calls `cat` or a generic file-read tool and receives the bytes, they enter the model context. A safe consumption mechanism must use files as tool inputs without echoing contents, or inject credentials through a controlled tool/broker with output/log redaction.
- Define the sanitization boundary before raw prompts can reach persistent browser drafts/history, bridge logs, queues, telemetry or harness transcripts. Files should be outside the repository, session-owned, inaccessible to other sessions, and cleaned on session termination plus crash/expiry recovery. Paths and basenames must not contain credential fragments.

The last two criteria are architectural deductions, not accuracy guarantees supplied by a detector. Detection is probabilistic: retain an explicit manual mark-as-secret path and reviewable redaction behavior even if the hybrid benchmark is strong.
