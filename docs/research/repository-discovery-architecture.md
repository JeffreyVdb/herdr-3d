## Integration constraints

**Scanned repositories are not floors.** Current protocol rows require `session`, `building`, and `same_building`. The browser drops a row without a nonempty `session`, uses that session as its popup key, and labels every result with its floor. Appending discovery rows with an empty/fabricated floor is therefore insufficient. Introduce an explicit source and stable item identity, with optional floor provenance, and update parser, rendering, search keys, popup keys, and empty/help text. [`internal/proto/reporefs.go:54`](../../internal/proto/reporefs.go#L54), [`game/src/laptop/repoSearch.ts:40`](../../game/src/laptop/repoSearch.ts#L40), [`game/src/laptop/repoSearch.ts:93`](../../game/src/laptop/repoSearch.ts#L93), [`game/src/laptop/repoSearch.ts:165`](../../game/src/laptop/repoSearch.ts#L165)

**GitHub origin lookup is optional metadata, not discovery.** The existing resolver runs `git remote get-url origin` and accepts only GitHub remotes; a local-only or non-GitHub repository returns an empty result. It has a default two-second subprocess timeout and five-minute cache, beneath the hub's additional thirty-second cache. Detect checkout markers independently and always retain the local path, including repositories without a GitHub remote. [`internal/gitremote/gitremote.go:39`](../../internal/gitremote/gitremote.go#L39), [`internal/gitremote/gitremote.go:91`](../../internal/gitremote/gitremote.go#L91), [`internal/gitremote/gitremote.go:142`](../../internal/gitremote/gitremote.go#L142), [`internal/server/repos.go:22`](../../internal/server/repos.go#L22)

**Completion already has stale-list behavior.** Each popup asks once, immediately displaying cached rows; another query ranks locally. Changes signaled through the settings book mark the source stale and notify an open popup. A failed refresh preserves existing rows. A catalog revision/update notification can reuse that mechanism, but a periodic scan completing without a settings change will need its own notification or revision. [`game/src/laptop/repoSearch.ts:132`](../../game/src/laptop/repoSearch.ts#L132), [`game/src/laptop/repoSearch.ts:171`](../../game/src/laptop/repoSearch.ts#L171), [`game/src/laptop/repoSearch.ts:203`](../../game/src/laptop/repoSearch.ts#L203)

**Do not use the file completion index as the discovery walker.** It indexes files inside already known checkouts with `git ls-files`/`rg --files`; it deliberately never walks the disk. Its cancellation, one-build-at-a-time, and cached-snapshot pattern is useful precedent for a separate repository catalog. The app wires that service with a bridge-lifetime context and waits for shutdown. [`internal/fileindex/index.go:1`](../../internal/fileindex/index.go#L1), [`internal/fileindex/index.go:62`](../../internal/fileindex/index.go#L62), [`internal/app/world.go:768`](../../internal/app/world.go#L768)

## Recommended implementation shape

These are proposed semantics, not existing behavior:

1. Add **Repository discovery** as a new bridge-stored Settings section adjacent to Repositories. Allow adding/removing several absolute scan roots and configuring the refresh interval in minutes, default **10 minutes**. Explain that paths belong to the bridge host. Empty roots disable discovery without affecting floor completion. Include scan status, repository count, last successful refresh, readable per-root errors, and a manual refresh action.
2. Introduce a small backend discovery/catalog service, wired in `internal/app`, with immutable result snapshots. Scan once after startup/configuration changes and periodically thereafter. Allow one scan at a time, cancel obsolete generations, reject late results from removed roots, and stop cleanly with the bridge context. Keep filesystem work and origin lookup off the hub event loop; `Hub.Run` serializes client commands and world updates. [`internal/server/hub.go:701`](../../internal/server/hub.go#L701)
3. Use the benchmark-selected walker to locate `.git` directories **and files** (including linked worktrees). Check the marker before enumerating each directory and stop at checkout boundaries, skipping the entire checkout contents. Recurse through grouping directories without a fixed depth; do not follow child symlinks. Embedded repositories/submodules require explicit additional roots; bare repositories are outside initial scope. No arbitrary dependency-name exclusions are needed. Explicitly document this policy and canonicalize explicit root aliases.
4. Persist scan roots and interval with a schema migration and publish validated settings/status to all clients. A separate discovery state is a clean fit for the requested new section; extending `repo_refs` is also possible, but requires changing its Go/TypeScript state, validators, persistence, and events together. Older bridges must keep existing floor completion and the existing toggle working.
5. Merge the latest catalog into both `worker.repos` and `hire.repos` server-side. Preserve current same-building/other-building ordering; place additional discovered entries deterministically afterward. The existing all-buildings toggle continues to govern floor sources, independently of explicitly configured scan roots.
6. Deduplicate repeated/overlapping roots and floor/catalog matches using canonical checkout paths. Resolve a floor's subdirectory to the checkout root before matching; `gitops.TopLevel` already provides that operation. Merge normalized GitHub URL-only floor references with discovered local checkouts, preferring the usable local path. Do not conflate unrelated repositories merely because their basenames match. Define which checkout wins when multiple clones/worktrees share a remote; keep the policy deterministic and show the selected path. [`internal/gitops/gitops.go:245`](../../internal/gitops/gitops.go#L245)
7. Local discovered rows insert their absolute checkout path as plain text, quoted when needed, preserving current completion insertion rules. Origin metadata may improve labels/search, but must not make a local Git repository unavailable. Include a stable catalog identity rather than borrowing a floor session. [`game/src/laptop/repoSearch.ts:64`](../../game/src/laptop/repoSearch.ts#L64)

## Acceptance and verification

- Multiple roots and the ten-minute default interval survive bridge restart and synchronize across connected clients. Invalid/duplicate paths and nonpositive/invalid intervals produce field-specific feedback.
- A newly cloned repository appears after the next scheduled or manual refresh; deleting a repository or removing a root removes its entries after a successful refresh. A temporarily unreadable root reports an error without erasing another root's results; preserve that root's previous successful snapshot until a complete successful replacement exists.
- Discovery includes ordinary checkouts, `.git` file worktrees/submodules under the documented traversal policy, repositories without origin, and non-GitHub origins. Cover roots that themselves are repositories, spaces/unicode, symlink aliases, overlapping roots, nested repositories, and unreadable/missing roots.
- Combined floor/discovery completion has no duplicate row for the same chosen repository identity; matches by canonical path, floor subdirectory, remote spelling/case/`.git` suffix, and overlapping scan roots are covered. Distinct repositories with the same basename remain distinguishable.
- All shared completion surfaces receive discovered results: transcript, Prompt, Hire, and Start run. Selection inserts the intended local path, existing un-cloned floor entries still insert their GitHub URL, and existing file completion remains unchanged.
- Scheduled refresh never blocks typing or client commands. Existing rows remain usable during a scan; an open popup refreshes on catalog change, and a removed root's stale in-flight result cannot reappear.
- Verify single-flight scans, interval changes, cancellation, shutdown, per-root failure recovery, settings migration, malformed protocol state, and compatibility with a bridge that lacks discovery support.
- Benchmark the supplied `/home/jeff/devel/jeffreyvdb` and `/home/jeff/devel/kiswe` roots, reporting exact traversal/exclusion policy, repository counts, repeated elapsed/CPU measurements, and environment/cache limitations. Set a concrete performance target from those measurements before implementation acceptance.
