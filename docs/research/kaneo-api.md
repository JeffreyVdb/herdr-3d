# Kaneo API research

Investigated 2026-10-07. Research only; no implementation or remote mutations. The user's instance is `https://tasks.example.org`; its public [deployment OpenAPI schema](https://tasks.example.org/api/openapi) is the authoritative endpoint contract for this integration. The schema reports API version `1.0.0`, which does not identify a Kaneo release or source commit. Official documentation and source were also checked; source links below pin upstream commit `6bd0c1ac42164ec2604a2e74538f6e084c684641` (2026-10-07). They explain behavior but do not prove the instance runs exactly that commit. Authenticated observations below were supplied by the main investigation; this documentation investigator did not access the supplied API key.

## Findings

Kaneo supports the requested workflow: authenticate with an API key, list accessible workspaces, and list projects in a selected workspace. Kaneo calls workspaces **organizations** in its authentication API. Store workspace and project IDs, displaying names in the UI. A key authenticates as its owning user; it does not automatically authorize every workspace or project. [Official authentication docs](https://kaneo.app/docs/api-reference/authentication), [deployment schema](https://tasks.example.org/api/openapi), [workspace authorization source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/utils/validate-workspace-access.ts), [project listing source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/project/controllers/get-projects.ts).

An integration needs an instance URL alongside the API key. The user's API base is `https://tasks.example.org/api`; the hosted service's schema advertises `https://cloud.kaneo.app/api`. Self-hosted instances normally expose `<public-origin>/api`. A running instance exposes its own OpenAPI document at `/api/openapi`, which the official docs recommend as the best match for its installed version. Normalize the configurable origin/API base consistently; retain the web origin for links. [Official introduction](https://kaneo.app/docs/api-reference/introduction), [cloud schema](https://cloud.kaneo.app/api/openapi), [deployment schema](https://tasks.example.org/api/openapi).

## Read-only deployment verification

The main investigation used the supplied key against `https://tasks.example.org/api` on 2026-10-07. No key, private user identity, workspace/project names, or resource IDs are recorded here. All requests were read-only; no tasks, comments, projects, keys, or workspace settings were created/changed.

| Request | Observed result |
| --- | --- |
| `GET /user/me` with Bearer key | 200, authenticated identity returned. |
| `GET /auth/organization/list` with Bearer key | 200, two accessible workspaces. |
| `GET /project?workspaceId=<id>` for each workspace | 200, one project in each workspace, two total. Includes IDs, `workspaceId`, `slug`; project-list `columns` are empty, consistent with the schema. |
| `GET /column/<projectId>` | 200, four columns: To Do (`to-do`), In Progress (`in-progress`), In Review (`in-review`), Done (`done`, `isFinal=true`). |
| `GET /task/tasks/<projectId>?limit=100&page=1&relatedPage=1` for both projects | 200, `{data,pagination}` response; both projects currently have zero tasks. Pagination: `total=0`, `page=1`, `pageSize=100`, `totalPages=1`, `relatedPage=1`, `relatedPageSize=100`, `relatedTotalPages=1`. |
| `GET /auth/organization/list` with deliberately invalid credential | 401 Unauthorized. |

These observations establish that credentials, dropdown discovery, and board/column reads work on the actual instance. Empty projects prevented live task-detail/comment/status/reorder verification; those contracts remain supported by the deployment schema and upstream source. Larger-page pagination and rate-limit behavior were not provoked.

## Authentication and testing settings

Create a key in Kaneo under **Settings → Account → API Keys** (Developer section). The full key is shown once; revoke or rotate it there. The documented request header is `Authorization: Bearer <api-key>`. Upstream also accepts `x-api-key`; its `/auth/*` handler translates a verified Bearer API key into the header expected by Better Auth, so the organization endpoint can use the same documented Bearer header. Use one header consistently. [Official authentication docs](https://kaneo.app/docs/api-reference/authentication), [application authentication source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/utils/authenticate-api-request.ts), [auth route bridge](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/index.ts#L678).

Recommended read-only **Test settings** sequence: use the draft URL/key to request `GET /user/me`, then `GET /auth/organization/list`; show the authenticated account and populate the workspace selector on success. An empty workspace list is a successful authentication with no workspace choices, not an invalid key. Test should not save drafts or mutate Kaneo's active organization. For floor configuration, fetch `GET /project?workspaceId=<chosen-id>` and validate the selected project still belongs to that workspace. These are design recommendations derived from the available endpoints. [Deployment schema](https://tasks.example.org/api/openapi).

API keys may be restricted by scope as well as user membership/roles. Upstream mutating application routes intersect any explicit key permissions with workspace permissions, including `task:update` for status/reorder/comments. A successful read-only test does not prove permission to mutate tasks. Restricted project membership is applied to project lists and individual resource requests. [Permission source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/utils/require-workspace-permission.ts), [workspace/resource middleware](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/utils/workspace-access-middleware.ts), [project listing source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/project/controllers/get-projects.ts).

Keep the key on the Herdr backend, mask the settings field, and return only a configured flag or masked hint when reading settings. The official docs explicitly direct integrations to server-side secret storage and warn against personal keys in shipped frontend JavaScript. Actual storage should follow Herdr's settings/secret conventions. [Official introduction](https://kaneo.app/docs/api-reference/introduction), [official authentication docs](https://kaneo.app/docs/api-reference/authentication).

## Endpoint contract

All paths in this table are relative to the configured API base. The methods, required parameters, and response types are present in the [user's deployment OpenAPI document](https://tasks.example.org/api/openapi).

| Purpose | Endpoint | Contract |
| --- | --- | --- |
| Test identity | `GET /user/me` | Current authenticated user. |
| Workspace selector | `GET /auth/organization/list` | Array of organizations/workspaces; the generated schema leaves item fields unspecified. The Kaneo web app uses the same organization-list operation. |
| Project selector | `GET /project?workspaceId=<id>` | Array of projects with `id`, `workspaceId`, `name`, `slug`, icon, archive metadata, and statistics. Archived projects are excluded by default; `includeArchived=true` includes them. No pagination parameters are declared. |
| Validate project | `GET /project/<id>` | Project details, including its owning `workspaceId`. |
| Board/task list | `GET /task/tasks/<projectId>?page=1&limit=100` | `{data, pagination}` board response, with tasks nested under columns and virtual buckets. |
| Task details | `GET /task/<id>` | Task fields plus assignee; `view=detail` is available, as is compact `view=board`. Detail includes current workspace ownership. |
| Workflow columns | `GET /column/<projectId>` | Columns ordered by position, with real column ID, slug, display name, icon/color, and `isFinal`. |
| Change status | `PUT /task/status/<id>` | JSON `{ "status": "<column-slug>" }`; returns the updated task. |
| Reorder/move cards | `POST /task/reorder` | JSON `{projectId, tasks:[{id,position,status?}], expectedTasks?:[{id,position,status}]}`; preserves other fields. |
| Comments | `GET /comment/<taskId>` | All comments oldest first, including author metadata; no pagination declared. |
| Activity | `GET /activity/<taskId>?limit=100` | Comments and system events newest first. Optional `limit` is 1–100; omitted means full feed. |
| Add comment | `POST /comment/<taskId>` | JSON `{ "content": "..." }`, length 1–10,000; returns stored activity row. No write was performed during research. |
| Compatibility comment route | `POST /activity/comment` | JSON `{taskId,comment}`; equivalent comment creation for the activity-feed client. |
| Resolve display ticket | `GET /task/by-ticket-id/<PROJECT-123>?workspaceId=<id>&projectId=<id>` | Ticket lookup can be ambiguous across accessible projects/workspaces; 409 requests narrower scope. Prefer stored task IDs. |

The workspace naming is not a guess: upstream maps Better Auth's organization model to `workspace`, and the web application's workspace fetcher calls `authClient.organization.list()`. [Authentication model mapping](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/auth.ts#L396), [workspace fetcher](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/web/src/fetchers/workspace/get-workspaces.ts).

## Task identity, state, and links

A task has a string `id`, a string `projectId`, a nullable per-project numeric `number`, title, nullable description, priority, status, dates, position, and assignee metadata. Its display identifier is `<project.slug>-<task.number>`, such as `KAN-12`. The numeric task number alone is not globally unique; store an identity that includes provider, instance, workspace/project scope, and the task's actual string ID. This is a design implication for Herdr models that presently assume a GitHub repository plus integer issue number. [Task and project schemas in deployed OpenAPI](https://tasks.example.org/api/openapi), [task response source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/response.ts).

The deployed Task/BoardTask schemas do **not** provide `updatedAt` or `closedAt`. `createdAt` is available, but must not be relabeled as an update/close timestamp. Kaneo activity can describe changes, yet no verified contract establishes a canonical completion time suitable for GitHub's recent-closed window. Recommended initial behavior: leave unsupported timestamps absent and retain final-column tasks within the bounded result cap; do not apply a fabricated seven-day completion filter. [Deployment task/board schemas](https://tasks.example.org/api/openapi).

`task.status` stores a **column slug**, not a column database ID. Workflows are customizable. Completion is represented by a column's `isFinal=true`, not by assuming the slug is `done`. `planned` and `archived` are virtual statuses outside ordinary columns. In a board response, `columns[].id` is also the slug; the dedicated `/column` response uses the actual column ID. Avoid interchanging those two shapes. [Deployment schema](https://tasks.example.org/api/openapi), [column schema/source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/column/response.ts), [valid statuses source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/validate-task-fields.ts), [completion source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/task-is-completed.ts).

There is no dedicated task-close operation in the deployed schema and no GitHub-style close reason. Recommended initial behavior: advertise the generic Close capability as unsupported and let the user complete a task by moving it to an actual `isFinal` workflow column through the status endpoint. Multiple final columns are valid; present their real names. Reopening needs a nonfinal target or the previous status; it cannot be inferred universally. Archiving is a separate action and must not be silently substituted for completion. These are proposed UI semantics, not Kaneo API guarantees. [Deployment schema](https://tasks.example.org/api/openapi), [completion source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/task-is-completed.ts).

The reliable task URL shape is `<web-origin>/dashboard/workspace/<workspaceId>/project/<projectId>/task/<taskId>`. Upstream can also produce friendly URLs `/<workspaceSlug>/task/<projectKey>-<number>/<optional-title-slug>` when it can safely identify the project. The full ID path is its fallback and avoids slug changes or ambiguous ticket keys. [Task link builder](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/web/src/lib/task-link.ts).

## Listing, pagination, and descriptions

Board list responses contain `data.columns[].tasks`, `data.plannedTasks`, and `data.archivedTasks`; they are not flat arrays. Flatten deliberately and deduplicate by string task ID when combining metadata continuations. The board also provides project identity/name/slug/workspace and column `isFinal` flags. [Official introduction](https://kaneo.app/docs/api-reference/introduction), [deployment board schemas](https://tasks.example.org/api/openapi).

Task pagination is always bounded: default limit 50, maximum 100. Follow `pagination.totalPages`; for **each task page**, follow `relatedPage=1..pagination.relatedTotalPages` if all labels, external links, and columns are required. Related rows have separate page size 100. Filter parameters are `status`, `priority`, `assigneeId`, `dueBefore`, `dueAfter`; sorting uses `sortBy` (`createdAt`, `priority`, `dueDate`, `position`, `title`, `number`) and `sortOrder` (`asc`, `desc`). Do not copy a generic `filters`/`sort` example from an index into the implementation: the deployment schema and source declare these concrete query parameters. [Deployment schema](https://tasks.example.org/api/openapi), [list controller](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/controllers/get-tasks.ts).

Descriptions above 64 KiB may be omitted from list/board responses with `descriptionDeferred=true`; `null` in that summary does not mean the stored text is empty. Fetch task detail for full text. `GET /task/<id>/description` supports bounded description pages with `offset`, optional `version`, and response `{content,version,nextOffset}`; a 409 on changed version requires restarting. The deployed schema uses `content`, despite indexed documentation examples that may say `description`. [Deployment schema](https://tasks.example.org/api/openapi), [task response source](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/response.ts).

Reordering should use the dedicated narrow operation rather than full task replacement. `expectedTasks` is the previous **complete contents of affected columns**, not merely the moved cards; upstream validates the snapshot and rejects stale ordering with 409. If reordering is included in the feature, refresh on conflict and do not retry against an old snapshot. [Deployment schema](https://tasks.example.org/api/openapi), [reorder controller](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/task/controllers/reorder-tasks.ts).

## Errors and rate limits

Official docs distinguish 400 (parameters), 401 (missing/invalid/expired credential), 403 (workspace/permission), 404 (resource/path), 429 (rate limit), and 5xx (service health). The deployed schema also reports 503 for timed-out board reads and 409 for stale reordering/ambiguous ticket lookups. Some unknown-resource application routes can return 400 because workspace resolution failed; clients should not assume every deleted resource produces 404. [Official introduction](https://kaneo.app/docs/api-reference/introduction), [deployment schema](https://tasks.example.org/api/openapi).

Upstream config enables per-key rate limiting at **100 requests per 60 seconds** by default; individual key records can override limits or carry a remaining quota/expiry. Important implementation caveat: the custom application's key verifier returns no valid result on exhaustion, and application authentication can then answer **401**, whereas the official docs list **429** generically. Do not claim every 401 proves the key is invalid forever. Debounce dropdown loads, cache by instance/credential/workspace, bound concurrency, and use conservative retries for reads. These mitigations are recommendations; this investigation did not consume quota deliberately or provoke limits. [Auth configuration](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/auth.ts#L652), [key verifier](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/utils/verify-api-key.ts), [application authentication](https://github.com/usekaneo/kaneo/blob/6bd0c1ac42164ec2604a2e74538f6e084c684641/apps/api/src/utils/authenticate-api-request.ts).

## Proposed settings behavior for the ticket

Global Kaneo settings: configurable instance URL, masked API key with replace/remove support, read-only Test, Save, and optional default workspace chosen from API-fetched workspaces. Floor settings: issue-provider choice (`GitHub` or `Kaneo`), workspace initially prefilled from the global default but overridable, and project selected from the chosen workspace's API-fetched list. Save explicit workspace/project IDs as the floor binding; changing the global default should prefill new configuration, without silently moving an existing floor to a different workspace. This persistence interpretation is a recommendation for predictable behavior and should be stated in the ticket.

Changing workspace must clear a project from the prior workspace and fetch the new choices. Failed fetches, empty lists, lost access, and removed/archived resources need actionable feedback; do not turn a transient fetch failure into loss of saved configuration. Changing provider must not reinterpret GitHub numeric IDs as Kaneo task IDs. GitHub credential configuration remains out of scope; its existing CLI behavior should remain available.
