# Dictation-compatible hiring: repository architecture

Repository inspection on 2026-10-09. This is implementation research, not an implementation or a report of live model tests.

## Existing UI and input behavior

The game already has a command palette (#147), opened by a top-bar control or Cmd/Ctrl+P. It is a native text field in a modal dialog, with autofocus, focus restoration, composition-aware Enter handling and stopped keyboard propagation. However, it searches existing action labels and Enter runs the selected result; it does not interpret natural language. Reusing its input/focus pattern is appropriate, but treating dictated prose as a fuzzy palette query could select the wrong action. Add a distinct natural-language bar or explicit mode, accessible by mouse as well as a shortcut. See [palette.ts](../../game/src/ui/palette.ts#L71), [its Enter handler](../../game/src/ui/palette.ts#L297), and [global opener](../../game/src/app.ts#L2580).

Global game controls already ignore typing targets and open dialogs. A new bar must also release held movement, stop walking, capture its Enter/Esc, respect `isComposing`, keep its DOM input stable across status updates, and restore focus on close. Standard input/paste events accept text inserted by external dictation software; no microphone or speech recognition is required. The relevant paths are [onKey](../../game/src/app.ts#L2430) and [openPalette](../../game/src/app.ts#L2599).

## Existing hire path to reuse

`App.openHire` resolves the current office floor and first free, unreserved desk, blocks sleeping/transitional floors and occupied desks, and opens the hire dialog. [App.openHire](../../game/src/app.ts#L1203). The dialog accepts `HirePrefill { prompt, choice: { harness, model, effort } }` ([HirePrefill](../../game/src/ui/hire.ts#L74)); its submit path resolves images, reserves the desk, sends `worker.hire`, clears the submitted draft only after success, and handles the case where the worker starts but its initial prompt is not delivered ([hire()](../../game/src/ui/hire.ts#L864)).

Under the latest user requirement, Enter interprets the command and opens a populated review dialog; it never launches directly. Reuse `HirePrefill` and the existing Hire dialog where practical, adding dynamic accordion sections rather than another review step. Resolved values appear in collapsed summaries and can be overridden; missing/invalid fields open for selection. Final explicit Hire confirmation passes the reviewed values to a shared coordinator that retains existing floor/desk/capacity/error/toast behavior. Existing typed wire args include session, desk, harness, exact model ID, effort, optional label/cwd/worktree and prompt ([WorkerHireArgs](../../internal/proto/proto.go#L687)).

The bridge's `beginHire` is the authoritative boundary: it validates the harness/model/effort tuple, prompt size/shape and folder, checks desk occupancy and concurrent reservations and hard caps, and starts the asynchronous hire. Keep it as the only launch path. See [beginHire](../../internal/server/hire.go#L373), [desk/cap checks](../../internal/server/hire.go#L410), and [allowlisted CLI templates](../../internal/herdr/control.go#L150). Claude effort is `--effort`; Codex uses `model_reasoning_effort`.

## Model and effort resolution

Use the bridge's snapshot `world.hire_options`, not a fixed list invented in a prompt. The bridge queries installed Claude Code and Codex model catalogs during startup; a failed probe retains only that harness's fallback catalog ([discoverHireOptions](../../internal/app/models.go#L12)). Model IDs, readable labels and each model's supported efforts are available. Common efforts are the intersection across a harness's models; `extra_efforts[model]` adds that specific model's remaining efforts ([catalog representation](../../internal/harness/models.go#L60), [effortsFor](../../game/src/world/settings.ts#L104)). Display names are presentation only; submitted values remain exact launch IDs ([modelLabel.ts](../../game/src/world/modelLabel.ts#L1)). Server validation checks the current catalog again ([validHireIn](../../internal/server/settings.go#L44)).

**Effort is required by the user's follow-up instruction.** If absent, keep the pending hire and ask for effort before sending any `worker.hire`. Show the selected model's supported efforts and accept a dictated reply such as “high.” An unsupported effort also requires correction. Preserve the task and previously resolved fields while asking.

Use the same dynamic review dialog to select missing effort and override model/harness. Changing the model updates effort choices: preserve a still-supported explicit effort, otherwise clear it and expand Effort. A dictated follow-up only edits the pending review. Even when every value was supplied initially, show all final values and wait for explicit Hire confirmation. Late interpretation responses must not overwrite newer human edits.

Do not pass missing or invalid natural-language fields through `resolveChoice`/`resolveVisibleChoice`: those functions intentionally replace unknown models with the first option and choose `high` or the first effort ([resolveChoice](../../game/src/world/hire.ts#L24)). Likewise `hire.prepare` offers floor defaults/last-hire defaults; those are UI conveniences, not evidence that the user supplied required effort ([choice](../../internal/server/hire.go#L256)). Natural-language state must distinguish omitted from explicitly selected fields.

The example “Claude on GPT-5.5 Haiku” mixes a harness, a GPT name and a Claude model family. Never silently substitute a launchable model. Resolve unambiguous aliases against exact IDs/readable labels in the catalog; otherwise ask which supported model/harness was intended. The fallback catalog has no Haiku entry ([fallback](../../internal/server/settings.go#L18)); actual availability depends on the live installed-harness catalog.

## Intent/extraction seam

Add a small feature package behind existing feature-agnostic `ai.Classifier`/`ai.LLM` interfaces ([interfaces](../../internal/ai/ai.go#L53)). Keep the provider integration unchanged. Jev supports several yes/no scoring questions in one request, capped at 16, but returns scores rather than task/model strings ([ClassifyMany](../../internal/ai/jev.go#L67)). It can gate explicit hire intent and separately identify explicit other game-action intent. A negative hire score alone cannot tell “unsupported action” from “unclear intent.” The configured LLM can perform structured intent plus field extraction in one call, or extract only after a Jev gate. Choose between them using the parent's live comparison results rather than assuming a combination is better.

Use separate outcomes: `hire`, `unsupported`, `unclear`, and `needs_input`. Explicit requests to hire/spawn a game agent are eligible; descriptions of hiring, quoted instructions, negations, speculative language and tasks mentioning spawning must not trigger hiring. Clear other game actions say “Not supported yet.” Ambiguous intent says the intent is unclear even though hire is the only implemented action. Missing/invalid fields within a clear hire ask a concrete follow-up, especially effort. Provider errors or malformed output are operational errors, not unclear intent, and never spawn.

Bound each interpretation, parse a strict schema, validate IDs/effort against the catalog, retain raw text, and preserve the task verbatim through validated source spans. Existing `packup` demonstrates classifier gating, exact-substring extraction and rejection of invalid spans ([packup](../../internal/packup/packup.go#L139)). Existing AI calls already have shared concurrency, timeout and retry limits ([service defaults](../../internal/ai/service.go#L18)). Do not let an LLM pick arbitrary commands or shell strings.

## Verification and ticket conventions

Browser E2E fixtures already record outgoing commands and simulate hires; [hire-composer.spec.ts](../../game/e2e/hire-composer.spec.ts#L23) counts `worker.hire`. [ai-integration.spec.ts](../../game/e2e/ai-integration.spec.ts#L6) starts fake Jev/OpenAI endpoints, and [fixture-ai.ts](../../game/tools/fixture-ai.ts#L1) also supports real endpoint calls. A new E2E should fill/paste dictated text, press Enter, inspect the populated review and assert zero hires before confirmation, including for a complete request. Unsupported/unclear/negated/quoted requests emit zero hires. Conflicting selections open for correction. Missing effort expands a selectable section; a valid dictated reply updates the review and still emits zero hires. Explicit Hire confirmation emits exactly one hire with the reviewed task and selections. Test model overrides, compatible/incompatible effort preservation, visible collapsed summaries, cancellation and late responses after human edits. Assert repeated confirmation does not duplicate spawns, and timeout preserves draft. A real-provider interpretation run is distinct from a real-harness launch test; label evidence accurately.

The repository uses numbered GitHub issues throughout docs and decisions and includes a provider-neutral GitHub/Kaneo tracker in the app. No issue template was found under `.github` (only CI/release workflows). Existing architecture issues worth referencing in the new ticket: #147 command palette, #92 AI integration, #110 exact-span extraction, #200 readable model labels. Creating the ticket is assigned to the parent.

## Configurable background hiring (added user scope)

The server already performs hiring asynchronously: `beginHire` reserves the desk/name and starts `runHire` in a goroutine ([start](../../internal/server/hire.go#L458)). It sends the final request ack only in `finishHire`, after workspace creation, agent startup, trust handling, observation and the initial-task delivery attempt ([runHire](../../internal/server/hire.go#L621), [finishHire](../../internal/server/hire.go#L992)). Therefore “do not wait for Claude ready” is a client-interaction requirement: return control immediately while these existing server steps continue. No early acceptance ack or additional server job system is necessary for the basic requested behavior.

Currently `HireDialog.hire()` sets a loading state and awaits the final `worker.hire` response with a 90-second client timeout ([submit](../../game/src/ui/hire.ts#L864), [timeout](../../game/src/net/client.ts#L137)). Success closes the dialog, may transition the player to the new laptop, and reports the worker/desk. There is already a useful detached path: Esc closes the dialog without cancelling the hire, its generation guards prevent a late response changing a newer dialog, and a late response only toasts ([close handling](../../game/src/ui/hire.ts#L342), [response handling](../../game/src/ui/hire.ts#L917)). Automatic laptop navigation is a separate browser setting, enabled by default, and waits for the worker's arrival animation ([goToNewHire](../../game/src/app.ts#L1362), [HirePrefs](../../game/src/ui/hirePrefs.ts#L18)).

Concrete seam: extend `HirePrefs` with a persisted browser-local “Hire in background” boolean and expose it next to the current go-to preference in Settings → Display ([settings row](../../game/src/ui/settingsSections.ts#L54)). Default it off to preserve existing users' behavior; enabling background mode suppresses automatic laptop navigation for that operation regardless of the go-to setting. Capture this setting when submitting so changes during startup do not alter the pending operation. Apply the same shared coordinator to conventional Hire-dialog submissions and resolved dictation hires.

After explicit Hire confirmation of valid reviewed fields (including explicit effort), capture the final immutable args and draft revision, synchronously acquire the client desk reservation, start the detached operation, and close the submitting dialog/bar immediately. Background mode must never skip the review. Do not wait for Claude readiness, an ack, or the arrival animation; do not call `goToNewHire` on its completion. For image-containing conventional hires, move upload resolution into the detached coordinator and hold the desk while uploads run. Existing code reserves only after uploads, so simply adding `close()` at the start would leave a window where another hire could reuse that desk. Distinguish the saved operation snapshot from subsequent edits to the reopened dialog.

On successful completion, show exactly **“Agent spawned successfully.”** and play a short beep directly through `audio.playUi('finished')` (or add a dedicated spawn tone), observing the existing master mute/volume and browser audio restrictions. `playUi` is already synthesized and independent of positional game sounds ([audio API](../../game/src/audio/index.ts#L27), [tone](../../game/src/audio/index.ts#L76), [implementation](../../game/src/audio/index.ts#L356)). Wire the beep and toast through the hire host/coordinator ([hireHost](../../game/src/app.ts#L531)); do not route completion through inbox entries, inbox pulses, desktop notifications or `Pings`. Keep normal task-completion/question inbox behavior separate from this new spawn confirmation.

Failures should release only their own reservation, show a direct error toast, retain the original draft/task for manual correction/retry, and leave the player's view and any newer dialog alone. A successful spawn with `prompted:false` is already a distinct partial failure: the worker exists, but the task was not delivered. Preserve the draft and present its delivery error rather than silently treating the hire as fully complete ([partial-success handling](../../game/src/ui/hire.ts#L927)). A Codex launch fallback also carries a warning ([hiredToast](../../game/src/ui/hiredToast.ts#L5)); preserve relevant warning information separately from the exact success-toast wording.

Deduplicate completion by operation/request identity; Enter while the same submission is being handed off must create one operation, and each final outcome must produce at most one beep/toast. Allow independent subsequent hires using other reserved-free desks. A disconnect/timeout does not prove a failed spawn: the network client explicitly warns that a disconnected command may still have run and drops unresolved request tracking ([request lifecycle](../../game/src/net/client.ts#L233), [disconnect](../../game/src/net/client.ts#L264)). `req_id` currently correlates replies, rather than providing server idempotency ([Command](../../internal/server/hub.go#L775)). Do not automatically repeat a launch after an unknown outcome. A basic first version can retain the task and show an outcome-unknown toast; if success notification after reconnection/page reload is required, add an explicit recoverable operation ID/status protocol and durable deduplication rather than inferring success from `worker.upsert` (which can precede prompt delivery).

Focused E2E: configure background mode; delay the hire ack; submit a valid hire; immediately assert dialog closed, player remains outside the new laptop, game controls work, and no premature success signal. Release a successful ack and assert exact toast, one beep, zero new inbox completion items and no navigation. Repeat with missing-effort follow-up, failed upload, launch failure, `prompted:false`, multiple pending hires, repeated Enter, reopen/edit while the old operation completes, mute, and disconnect/timeout. Verify the preference persists on reload and disabling it retains existing interactive hiring.
