## Problem and desired behavior

Today, using a credential without pasting it into an agent prompt requires SSH to the bridge host, manually creating a file, and remembering its path. Automate detection and file handling with explicit user confirmation: detect candidate credentials locally, show the entire original prompt with every detected occurrence highlighted, let the user individually ignore or correct matches, then preserve approved exact values in private files on the bridge host and replace their occurrences with references such as `Use the API credential in this file: /run/user/<uid>/h3d-secrets/<owner>/<opaque-id>`. Delete those files when the owning agent session ends, including recovery after failures/crashes.

## Viability and delivery gates

**Viable as a workflow with mandatory user review whenever any candidates are found.** Detection proposes matches; it never silently authorizes a replacement or send. The first delivery should establish the local sanitizer boundary, memory-only raw drafts, the full-prompt review screen, per-occurrence ignore/correction/manual marking, private owned files, references, retry behavior and lifecycle cleanup. This confirmation gate applies to every finding, including high-confidence provider/structure rules. The whole feature is behind an opt-in setting, off by default. Model inference is optional and must not become a dependency of the first delivery.

“Local” means the bridge host, with no external classifier and no provider token verification. The protection contract covers user-approved secret occurrences in supported model-input and persistence routes; explicitly ignored occurrences remain ordinary plaintext. It does not promise to recognize every possible credential. Preserve the original full integration/permission/lifecycle requirements below as delivery gates.

Before enabling extraction for a syntax, specify its file-byte contract: raw plaintext source bytes versus JSON/shell unescaping or URL percent decoding. Never infer this from a model span. Manual selection preserves the selected plaintext bytes. Before claiming protection through later tool use, demonstrate one concrete supported credential-consuming path that injects bytes without returning them to the model. Private files alone cannot enforce that guarantee for arbitrary shell reads, unrestricted tool output or other workers under the same UID.

## Feature setting

Put the feature behind an opt-in **Review prompt secrets before sending** setting in the existing Settings interface, **off by default**. Persist the enabled flag through the normal bridge settings mechanism and apply it consistently to supported submission/AI-preprocessing routes for that bridge.

- **Off:** follow the existing prompt flow; this feature runs no detection, opens no secret-review screen and creates no new secret files. Do not eagerly download/load its optional model or run background inference while disabled.
- **On:** scan locally and require the full confirmation flow below whenever any candidates are found. The setting enables detection and review; it never enables silent automatic extraction.
- A setting change invalidates affected pending review/confirmation state. Turning the setting off during a review cancels that pending submission and returns to its in-memory draft; it never forwards the original prompt automatically. A subsequent send is an explicit user action under the current setting. Existing owned secret files retain their normal run/lease/cleanup lifecycle when the setting is disabled.

## Required confirmation and review flow

1. **Scan before downstream use when enabled.** On Send, run local detection before AI preprocessing, external LLM calls or raw draft persistence. A completed scan with no findings follows the normal send path without an empty review screen; manual marking remains available in the composer.
2. **Show the whole prompt when anything is found.** Open a dedicated review screen containing the entire original prompt, with each proposed secret occurrence highlighted at its exact boundaries. Preserve whitespace, newlines, Unicode and surrounding context. Long prompts remain fully scrollable; users can navigate between matches without losing the full-prompt view. Do not substitute a list of snippets or mask away the text needed to judge a boundary.
3. **Make every occurrence independently overridable.** Each highlight is proposed for protection, pending final confirmation. Pressing it offers **Ignore this occurrence**, **Protect as file** (restore an ignored match), and boundary correction. Users can also select missed text and mark it as secret. Show a visible protected/ignored state and counts. Support keyboard and touch operation; do not convey decisions by color alone.
4. **Keep ignore local to this review.** Ignore applies to one occurrence in the current prompt revision, never a global/provider/session allowlist. Identical repeated values are independently controllable. Preserve an ignored occurrence verbatim in the submitted text and create no file for it. Review choices are authoritative: never globally replace all identical strings after the user ignored one. Resolve duplicate/overlapping detector spans without bypassing that occurrence's decision.
5. **Require an explicit final action.** **Confirm and send** applies the reviewed decisions, creates files only for approved spans and continues the intended submission. For an AI-preprocessing action, use an equally explicit **Confirm and continue** before that action. Display how many occurrences will be protected and ignored; explain inline that ignored matches stay plain text. Users can confirm with every match ignored. Ignoring the final match must never auto-submit. Do not add a separate approval dialog for each match.
6. **Keep consent tied to what was reviewed.** Bind the decision set to the prompt revision, source ranges and candidate set. Editing text or changing findings requires renewed review before send; pending scans, late model responses, stale tabs and API callers cannot reuse stale confirmation or add replacements after it. Retrying the identical confirmed submission preserves its per-occurrence decisions and idempotency. Routes without the review UI return a review-required state when they find candidates instead of bypassing it.
7. **Cancel without side effects.** Cancel/back returns to the in-memory composer without submitting, calling AI preprocessing or retaining new secret files. Keep the raw review prompt and pending choices in memory, out of drafts/localStorage, logs and telemetry. Create the final owned files only after confirmation, with existing rollback behavior on failed writes/sends. After confirmation, approved source occurrences become references; explicitly ignored occurrences follow ordinary plaintext submission/persistence rules. If the same literal is protected in one place and ignored in another, honor those separate decisions.

**Effect on viability and benchmarks:** false positives become review/correction effort rather than silent corruption of the prompt. A broader contextual detector may therefore be viable as a candidate generator even when it fails the unattended-extraction criteria used in the original investigation. Measure recall, exact boundaries/file bytes, false highlights per prompt, how often review opens on clean prompts, correction effort, review completion time and scan latency. Confirmation does not repair false negatives, partial boundaries or truncation by itself; manual marking and independent validation remain required. The results below are detector measurements, with no measured usability benefit claimed for this proposed screen.

## Investigation and actual benchmarks

Investigated on 2026-10-18 at `d24562ac5ec42ec9e9fa2a560683b5ff46ee73de`, using primary sources discovered through Alterlab and local CPU inference. This is a diagnostic pilot of 54 synthetic prompts: 36 credential occurrences in 32 positive prompts and 22 clean prompts. No real secrets or provider verification were used. There is no independent holdout; these results are not production guarantees. Shared Intel i7-10750H workstation, four PyTorch threads; timing is indicative.

| Detector/configuration | Exact secret extraction | Exact precision | Fully covered secrets | Clean prompts flagged | Short-prompt p50/p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Gitleaks 8.30.1, persistent Go API | 18/36 | 100% | 18/36 | 0/22 | 0.16/0.74 ms |
| detect-secrets 1.5.0, configured entropy thresholds applied | 14/36 | 43.8% | 22/36 | 6/22 | 1.9/5.4 ms |
| Knowledgator GLiNER PII small, threshold .5 | 24/36 | 42.1% | 25/36 | 16/22 | 77/230 ms |
| Fastino GLiNER2 privacy PII multi, threshold .5 | 27/36 | 42.9% | 30/36 | 13/22 | 244/584 ms |
| Gitleaks + GLiNER2, threshold .7 | 30/36 | 68.2% | 31/36 | 8/22 | Components above; no combined timer |

Gitleaks detected all 11 credential-like occurrences in the pilot provider group (not all format-valid; see follow-up), but missed many ordinary passwords and unknown prose tokens. Reusing its Go detector compiled rules once in 39 ms, with ~39 MiB peak RSS; starting the CLI per prompt instead cost ~907 ms p50. The Go library is the viable baseline.

The contextual models add recall but are not ready for unconditional automatic replacement. Partial passwords (including missing punctuation), extra surrounding text, multiline values and false positives break exact extraction. Full coverage alone is insufficient: an overbroad prediction can hide the secret while putting an unusable value in its file.

Long-input handling is mandatory. The small model truncated the longest input and missed its final secret. Default GLiNER2 took ~44–50 s on the 17 KB prompt, peaking at ~5.74 GiB. Its documented overlapping-chunk API reduced this to 10.8 s/~2.86 GiB in a single-repeat follow-up, but changed one long-tail prediction at .5/.7; the .7 chunked hybrid extracted 29/36 exactly. Cached model imports/load took ~12–14 s. The initial pilot did not measure ONNX; the follow-up below now measures published edge/small exports.

**Recommendation:** use persistent format detection plus structural boundaries and optional contextual suggestions, all subject to the mandatory full-prompt confirmation flow above. Confidence never bypasses review. Detector quality now needs evaluation together with review burden; the research probe and thresholds are not validated unattended operating points.

## Benchmark-hardening follow-up (2026-10-18)

Research only; no product implementation. The original 54-prompt pilot was used for development, then the experimental structure recognizer was frozen before authoring 138 fresh challenge prompts: 84 secret occurrences, 60 negatives, 35 positive and 30 negative template families. This is the same investigator and synthetic repeated templates, **not an independent production holdout**. No recognizer changes were made after inspecting challenge results. An incidental-word annotation was corrected by labeling explicit inserted value slots.

| Configuration / corpus | Exact extraction | Exact precision | Fully covered | Clean prompts flagged | Short-prompt p50/p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Gitleaks + research structure/prose recognizer, original pilot | 34/36 | 100% | 34/36 | 0/22 | 0.22/1.42 ms combined |
| Above + GLiNER2 literal-value descriptions, .7, original pilot | 35/36 | 83.3% | 35/36 | 7/22 | 220/280 ms model component |
| Frozen Gitleaks/structure recognizer, fresh challenge | 62/84 | 76.5% | 62/84 | 16/60 | 0.22/0.66 ms combined |
| Above + described GLiNER2, .7, fresh challenge | 75/84 | 46.3% | 75/84 | 59/60 | 208/230 ms model component |

The apparent 34/36, zero-clean-error operating point does not generalize: the fresh challenge exposes template references, redaction placeholders, function expressions and “the secret is 42 lines long.” Escaped quotes and a meaningful trailing period cause partial extraction; the frozen pattern path has two partial-only overlaps. Global placeholder exclusions also miss actual weak passwords such as `example`. This research recognizer is a feasibility probe, not code to promote into the product. Require a separately authored, substantially larger clean/credential evaluation before widening candidate coverage in the reviewed flow.

**Challenge limitation and paired control:** every clean challenge text has an appended generated request ID. That shared adversarial stressor amplifies model false positives; the 59/60 hybrid rate is not a representative real-world estimate. Removing only those identifiers and deduplicating gives 30 base clean templates. The unchanged .7 described model flags 15/30; combined with structure rules it flags 18/30 (structure alone 8/30). At .9 the raw model still flags 11/30. No rule/schema/threshold tuning was performed after this check. The control includes one unchanged positive anchor solely for the shared evaluator. Both the identifier sensitivity and ordinary clean-text errors block automatic deployment at these measured operating points.

The described .7 model improves the pilot hybrid from 30/36 at 68.2% precision to 35/36 at 83.3%, but still flags 7/22 clean prompts. Its tokenizer treats whole HTTP URLs as atomic words and the PII checkpoint has `max_width=8`; some exact query-value and punctuation-heavy password boundaries cannot be represented by the model at any threshold. Structural extraction is a necessary separate stage, not a confidence adjustment.

**CPU/deployment measurements:** GLiNER2 with 128-word windows/32 overlap/batch one takes ~4.69 s on 8,644 bytes and ~9.13 s on 17,064 bytes (three-repeat medians), versus the previous 6.6/10.8 s single-repeat chunked follow-up and ~44–50 s unchunked longest case. Narrow three-label 384/64/batch-one measured ~3.74/7.50 s. These are configuration bundles and shared-workstation measurements, not isolated causal comparisons. Cold load remains ~10.5–11.4 s and peak process RSS ~2.86 GiB.

Published ONNX exports were also measured offline, at .5 with the same five labels and bounded long-input windows:

| Configuration | Original-pilot exact | Clean flagged | Short p50/p95 | Peak process RSS |
| --- | ---: | ---: | ---: | ---: |
| Edge float32 | 25/36 | 17/22 | 16/25 ms | 829 MiB |
| Edge UINT8 | 3/36 | 3/22 | 13/23 ms | 540 MiB |
| Small UINT8 | 21/36 | 16/22 | 32/67 ms | 635 MiB |

Smaller artifacts are not equivalent detectors. Edge UINT8 at .3 recovers 16/36 but flags 15/22 clean prompts; at .7 it extracts none of the pilot secrets. At .5 both edge float32 and small UINT8 flag all 60 challenge negatives. Faster optional suggestions are plausible; unconditional automatic extraction is not supported. RSS includes interpreter/framework imports. The edge float32/UINT8 comparison holds checkpoint, labels and windowing fixed; no quantization-only speedup is claimed from comparison with a different model.

**Corrections to the initial investigation:**

- The pilot's 11 provider-group occurrences are credential-like strings, not 11 format-valid keys. Its OpenAI generator lacks the dedicated scanner grammar's marker/length and its HF generator permits digits; generic rules detected them. Keep malformed/unknown-token cases separate from valid format coverage.
- A fresh scanner-grammar-valid HF token is detected by Gitleaks at end-of-input, before whitespace/quotes/semicolons, but missed before a period, comma or closing parenthesis. Provider-prefix support is not sufficient prompt coverage.
- Current `worker.prompt` accepts at most 16,384 bytes (`internal/herdr/term.go`); the 17,064-byte pilot is an over-limit stress test. New beginning/middle/end probes at exactly 16,384 bytes all extract the quoted password exactly in ~11–12 ms for the pattern path including helper IPC. This is not an integrated send test.
- All model combinations above are accuracy replays with the frozen structure version. Model latency is component latency; pattern-path timings include both actual sequential scans. No complete UI/network/file-storage timing or representative bridge-host SLA has been established.

## Implementation scope

- Introduce one local sanitizer contract shared by prompt/answer submission, first hires, free-text and edited run prompts, and AI preprocessing. Separate preflight detection from confirmed materialization: preflight returns revision-bound per-occurrence candidates for review; confirmed materialization returns sanitized text and opaque owned secret references using the authoritative user decisions. Use exact original bytes, resolve overlap conflicts, preserve Unicode/newlines, handle repeated values independently, and validate Go UTF-8/Python character/JS UTF-16 offset conversion. Add deterministic parsing for PEM, headers, credential URLs, assignments, quoted passwords and multiline values. Model span boundaries alone are insufficient.
- Sanitize **before** `packup.detect` and `hire.interpret` call the configured LLM, not just immediately before agent input. Cover `internal/server/input.go`, `hire.go`, `launch.go`, `packup.go`, `hireintent.go`, and preview/retry/answer paths. Persist sanitized launch data only. Keep references intact through harness translation; avoid automatic `@file` expansion into model context.
- Address `game/src/ui/drafts.ts`, which currently writes text and composer segments to localStorage before Send. While the feature is enabled, secret-capable drafts must stay memory-only until safely transformed, or use detection before persistence; clear any raw persisted draft after transformation. Keep raw review text memory-only. Logs, errors, audit records, notifications, SQLite, downstream prompt previews and transcripts must receive replacements for approved secret occurrences. Explicitly ignored occurrences remain ordinary plaintext after confirmed submission; the original local review screen intentionally shows the entire prompt.
- Create files outside repositories and shared Drop Zones, under a private runtime directory (0700), files 0600, exclusive creation and no symlink following. Use random names without secret fragments; never append or normalize secret bytes. Do not rely on 0600 for isolation between workers sharing the same Unix UID; use owner-checked bridge handles, and separate sandbox/broker controls where stronger isolation is required.
- Make file consumption safe: generic Read tools or `cat` return bytes to the model and undo the protection. Provide native file-consuming tool inputs or a narrow credential-injection mechanism that does not return contents; avoid echo/tracing/verbose logs, and address credential-bearing tool output. File references alone protect the initial prompt, not all possible later tool use.
- Bind secret lifetime to the agent run/workspace, not a long-lived project/floor or an idle turn. Preserve files through supported idle/reconnect/resume, release on real session termination or explicit revoke, and lease to delegated consumers. Clean cancelled previews, failed sends/hires, and orphan files after restart/expiry. Persist ownership/expiry/opaque IDs only. Unlink cleanup is not a promise of secure disk erasure.
- Require the full-prompt review screen and per-occurrence ignore/restore, boundary correction and manual marking whenever any candidates are detected, regardless of confidence. Show masked inline file chips after approved replacements. Detection stays local and never validates tokens with provider APIs. When protection cannot scan/store safely, show an explicit recoverable state and keep raw text in memory; do not silently forward it to an external classifier or agent.
