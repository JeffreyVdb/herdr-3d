## Answer

**A worker gets the same skills, MCP servers, hooks and instructions on both accounts as long as it runs in the same `CODEX_HOME` folder.** Everything you configure yourself lives in the folder. What follows the account is only what OpenAI serves per sign-in: the model list, the built-in `codex_apps` connector server, plugins installed through ChatGPT, and workspace-managed policy.

**Naming:** the ticket calls the work seat "the Business seat". On the wire it is plan `team` (`account/read` `planType`). Codex's `PlanType::Business` is a different value, and `Team` is a workspace account (`is_workspace_account() == true`) but not business-like (`is_business_like() == false`, `B/protocol/src/account.rs#L68`, test at #L203). The eligibility below is about the wire value, not the product name.

**The work seat has no managed policy and nothing in it blocks hiring.** [R-live] `configRequirements/read` returned `requirements: null` on both homes, no config warning was raised, and there is no developer-instruction layer. [S] Codex does not even ask for a policy bundle on this plan: the work account's wire plan is `team`, and only Business, Enterprise and Education plans fetch one. So `--dangerously-bypass-approvals-and-sandbox`, `approval_policy=never` and `danger-full-access` are not refused, MCP servers, web search and network domains are not limited, and the model list is unrestricted. This is a property of the plan, not a guarantee: see "What #139 must report".

**#136 says workers need one auth home per account, so the real question is how to keep a second home's setup shared.** A fresh home starts bare (the work home today has no `config.toml`, no hooks, no MCP servers). The cheapest layout that keeps the setup shared, found in source:

1. Put skills in `~/.agents/skills`. It is read from `HOME`, not `CODEX_HOME`, so every home sees it with no linking. [R-live] The work home already lists all 27 of them.
2. Make each account's `config.toml` a **symlink** to one shared file. Codex follows the symlink when it writes (trust prompts, plugin toggles): see Row 4 below. This shares MCP servers, `approval_policy`, `sandbox_mode`, `features`, trusted projects, model choice and hook trust.
3. Link `AGENTS.md` (there is none today) and `plugins/` the same way. Keep `auth.json`, `sessions/`, the SQLite files, `models_cache.json`, `logs` and `.credentials.json` per home.
4. Give each home its own `hooks.json` pointing at the one `herdr-agent-state.sh`, and add its trust entry to the shared `config.toml` (the key contains the home's own path).

Codex has no include or extra-skills-path setting, and no `CODEX_CONFIG`-style override, so symlinks are the only mechanism found ([S] I found no such key in the config schema, `B/config/src/config_toml.rs`, nor in the docs; absence in source is weaker evidence than presence). The only existing multi-account tool that does this is [Ducksss/codex-profiles](https://github.com/Ducksss/codex-profiles) (`codex-profile init --share-with`, MIT, 188 stars, last push 2026-10-17). Per its README it symlinks `config.toml`, `AGENTS.md`, `AGENTS.override.md`, `rules/` and `plugins/` and never `auth.json`, `sessions/`, SQLite, skills or hooks. [Loongphy/codex-auth](https://github.com/Loongphy/codex-auth) (2830 stars, MIT) swaps only `auth.json` in one home, which shares everything by construction but is what #136 ruled out for simultaneous workers. Four more switchers (midhunmonachan/codex-profiles, xjoker/codex-switch, Lampese/codex-switcher, codex-accounts) were seen in search results only; **[U]**. A small herdr-owned provisioning step that creates the links is a better fit than adopting a tool: it is a handful of `ln -s` calls plus one `hooks.json`.

Corrections to the ticket's premises, from source [S]:

- The cloud bundle cannot carry `allowed_login_methods`, `allowed_chatgpt_workspaces`, `cli_auth_credentials_store` or `chatgpt_base_url`: they are stripped (`B/config/src/requirements_layers/layer.rs#L13`, `#L277`) and apply only from `/etc/codex/requirements.toml` or MDM, so they are machine-scoped.
- The developer-instructions key is `additional_developer_instructions` (capped at 10,000 tokens); `managed_config.developer_instructions` is only the label on the injected message.
- Precedence, low to high: system `requirements.toml`, cloud bundle, legacy `managed_config.toml`, MDM (`B/config/src/loader/mod.rs#L108-L130`). Requirements are constraints that `config.toml`, profiles and CLI flags are checked against, not defaults.

## Local setup on the two accounts (the ticket's first questions)

- **Same MCP servers, skills, hooks?** Inside one folder, yes by construction: a switcher changes only `auth.json`. [R-live] confirmed by starting an app-server on each folder: the work folder, being bare, has none of the MCP servers, hooks or trust, and the personal one has all of them; `skills/list` differs only by `infra-manager` (not in `~/.agents/skills`) and by timing of plugin skills. That is "this folder is bare", not "this account is different".
- **Hooks need review after a switch?** Not inside one folder: the trust key is the hooks file's path plus the hook position, and the hash is of the hook definition; neither includes the account [S]. It does return in any new folder, once per folder (Herdr leaves it to the player, `codexserver.go:682`).
- **MCP sign-ins after a switch?** Yes. Keyring entries are keyed by server and URL, and [R-live] the work home saw the personal sign-in for `code-intel` (see the table).

## What blocks hiring on the work seat

**Nothing found.** [R-live] No requirements, so no allowed-list for approval policies, sandbox modes, permission profiles, web search or login methods; no network domain rules; no MCP allowlist; no developer instructions; no models restriction. herdr-3d's launch shapes are therefore not refused. Permissions come from `--dangerously-bypass-approvals-and-sandbox` on the hire's TUI start and the embedded-fallback resume (`internal/herdr/control.go:202`, `:257`, `:267`), not from the server: the shared server is started as `codex app-server -c <trust> -c <features> --listen unix://…` with no approval or sandbox setting (`internal/codexapp/launch.go:151`). A remote resume refuses a permission override, and the thread keeps the permissions it was started with ([codex-shared-tui.md](codex-shared-tui.md) B9).

Not exercised: an actual hire on the work seat. I started no thread and no turn, so the effective thread settings were not read back. If requirements are ever null, there is nothing to downgrade, so this is not expected to differ.

In a fresh per-account home, `approval_policy` and `sandbox_mode` are unset, but that does not change the above: the hire's flag sets the thread's permissions and wake keeps them. It would matter only for a thread started without an override, which herdr-3d does not do. **[U]** Whether Codex re-checks a resumed thread's stored permissions against a policy that appeared after the hire; on a seat with no policy it is moot.

## What #139 must report when a policy refuses a hire

Today none applies; this is what #139 must handle if a seat's plan gains a bundle (the wire plan `planType` becomes a business-like, education or enterprise value; or a system `requirements.toml` appears). All from source [S], none observed live.

1. **Read the policy before launch.** `configRequirements/read` (no params; response `{requirements: ConfigRequirements | null, supportsIndependentSpeedModes?}`, `B/app-server-protocol/src/protocol/common.rs#L1469`, `…/v2/config.rs#L762`). `null` means nothing applies. `hooks`, `network` and `allowedApprovalsReviewers` are experimental, so `initialize` needs `capabilities.experimentalApi = true`. `config/read {includeLayers: true}` shows an `enterpriseManaged` layer when a bundle is active. The committed [policy_probe.py](codex-accounts-shared-setup/policy_probe.py) is a working read-only example.
2. **A refused mode is downgraded, not refused, in most cases.** A disallowed approval policy falls back to the first allowed one, a disallowed sandbox to read-only, with the startup warning "Configured value for `approval_policy` is disallowed by requirements; falling back to required value … (set by enterprise-managed requirements …)" (`B/core/src/config/mod.rs#L2300-L2334`). On `thread/start` that arrives as a `configWarning` notification (`B/app-server/src/request_processors/thread_processor.rs#L1433`); the response carries the effective `approvalPolicy` and `sandbox` (`…/v2/thread.rs#L188`). **#139 must compare the effective values with what the hire asked for and fail the hire with a plain reason**, since a worker silently running read-only is a stuck pane.
3. **The one hard error.** `approval_policy = "never"` with `danger-full-access` disallowed is rejected at config load (`core/src/config/mod.rs#L4259-L4268`): "`approval_policy = "never"` cannot be used because requirements do not allow `sandbox_mode = "danger-full-access"`; Codex would fall back to read-only permissions with approvals disabled. Choose an `approval_policy` based on what you need, such as `on-request`, or choose an allowed sandbox mode." Over the app-server it is JSON-RPC `-32600`, "failed to load configuration: …".
4. **Per-turn overrides** are rejected with `-32600` "invalid thread settings override: invalid value for `approval_policy`: …" (`B/app-server/src/request_processors/turn_processor.rs#L880`).
5. **Fail-closed on a broken bundle.** If the bundle cannot be loaded, Codex refuses to start threads: "Failed to load cloud config bundle (workspace-managed policies)." (`B/cloud-config/src/service.rs`); `thread/start` returns `-32600` with data `{reason: "cloudConfigBundle", errorCode, detail, statusCode?, action: "relogin"}` for auth failures (`B/app-server/src/request_processors/config_errors.rs#L16`). Suggested wording: "<alias>'s workspace policies could not be loaded. Sign in to <alias> again." The bundle is fetched at startup (5 attempts, 20 s) and cached for an hour in `cloud-config-bundle-cache.json`, so a restart on a flaky network is the likeliest trigger.
6. **Not an error, still worth saying.** MCP servers outside a policy allowlist are disabled without any message (`B/core/src/config/mod.rs#L2224`), and web search is clamped. A hire dialog on a managed seat should list `allowedWebSearchModes` and MCP availability from `mcpServerStatus/list` instead of letting a missing tool look like a bug. `configRequirements/read` omits `mcp_servers`, `plugins` and `apps`.

Suggested hire-failure messages (plain wording, as the ticket asks): "<alias> does not allow workers that run without asking. Its workspace policy limits approvals to <list> and sandbox to <list>." and "<alias> started the worker in read-only mode because of its workspace policy. Hire it on another account or ask the workspace admin."

## Reproduction and side effects

Read-only probe, committed next to this note: [policy_probe.py](codex-accounts-shared-setup/policy_probe.py) and its output, [probe-results.json](codex-accounts-shared-setup/probe-results.json). It starts `codex app-server` on stdio with `CODEX_HOME=<home>` and sends only `account/read`, `configRequirements/read`, `config/read`, `hooks/list`, `skills/list`, `mcpServerStatus/list`, `plugin/installed`, `model/list` and `app/list`. No thread, turn, login or config write. Every string value is replaced with `<str>` unless its key is on an allow list (names of skills, servers, plugins, connectors and policy enum values), so e-mails, account ids, tokens, hashes and paths cannot reach the output; the instruction text is reduced to a length.

```bash
python3 -I docs/research/codex-accounts-shared-setup/policy_probe.py ~/.codex-work "$PWD" > work.json
python3 -I docs/research/codex-accounts-shared-setup/policy_probe.py ~/.codex "$PWD" > personal.json
```

Side effects on the work seat, stated plainly as #136 did: the probe was run five times against `~/.codex-work`; the last run used a CLI-only `-c mcp_servers.code-intel.url=…` override, which made Codex read the stored `code-intel` sign-in from the keyring and contact that server's MCP endpoint to list its tools (a read, no token printed, nothing written). It did not change `auth.json` ([L] mtime unchanged at 2026-10-20 21:44:37, so no token refresh happened), and wrote no setting. It refilled `models_cache.json`, the logs and the queue/state SQLite files, and no `cloud-config-bundle-cache.json` was created. The personal home was probed three times, with the same effects. Source was read from a tarball of the pinned commit in `~/.cache/h3d-137-codex`; nothing from it was run.

Web sources, all read 2026-10-21 with the Alterlab tools: developers.openai.com/codex (config reference, requirements and managed configuration, skills, hooks, MCP, plugins, AGENTS.md); [Ducksss/codex-profiles README](https://github.com/Ducksss/codex-profiles) and [Loongphy/codex-auth README](https://github.com/Loongphy/codex-auth) for the tools.
